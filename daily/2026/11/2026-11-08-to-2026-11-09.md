## 1. Perplexity Teammates：从 AI 助手走向长期运行的 Agent 团队

**发布日期：2026-11-04｜重要性：A｜领域：AI Agent / AI 应用｜类型：产品发布**

Perplexity 发布了 Perplexity Teammates，定位为能够承担持续性工作的个人 Agent。

[Perplexity Teammates 官方发布公告](https://www.perplexity.ai/en-GB/hub/blog/teammates-are-agents-for-complex-ongoing-work?utm_source=chatgpt.com)

### 核心产品能力

它不是传统的聊天机器人，也不是简单的 Workflow：

- 用户给 Agent 指定长期工作目标。
- Agent 可以协调多个 Computer Session 和其他 Teammates。
- 跨任务保存项目目标、任务历史和共享文件。
- 持续监控外部变化，发现需要处理的问题。
- 可以在不同业务领域之间交接工作。
- 支持通过 Slack 与 Agent 协作。
- 执行过程中向用户报告进度，并在需要时申请批准。

官方举例：

一个 Sales Teammate 发现客户交易频率下降后，可以：

1. 查询客户历史订单。
2. 检查支持工单。
3. 分析交易下降原因。
4. 准备针对性的优惠方案。
5. 请求用户批准。
6. 继续跟进客户。

这实际上已经接近一个长期运行的业务 Agent，而不是单次问答。[Perplexity AI](https://www.perplexity.ai/en-GB/hub/blog/teammates-are-agents-for-complex-ongoing-work)

### 技术架构值得关注的地方

| 能力                  | 实现思路                             |
| ------------------- | -------------------------------- |
| Long-running Task   | Teammate 持续管理 Computer Session   |
| Memory              | 保存项目目标、任务历史和共享文件                 |
| Multi-Agent         | Teammate 可以委派工作给其他 Teammate      |
| Tool Integration    | 连接 Slack、GitHub、Gmail 等工具        |
| Execution Isolation | 每个 Teammate 使用独立执行环境和浏览器 Session |
| Credential Security | 保存的凭据加密处理                        |
| Human-in-the-loop   | 执行过程中提交审批和结果供用户检查                |

官方特别强调，不同 Teammate 的执行环境和浏览器 Session 相互隔离。[Perplexity AI](https://www.perplexity.ai/en-GB/hub/blog/teammates-are-agents-for-complex-ongoing-work)

### 成熟度与商业模式

- 当前状态：Web 端正式推出，但功能和用户范围仍在逐步扩展。
- 首批访问：Perplexity Max 用户。
- iOS：官方称后续推出。
- Max 官方月价：200 美元，年付 2,000 美元。
- 企业版：不能把消费者 Max 的开放范围直接等同于 Enterprise 全面开放。
- 单独的 Teammate 定价：未披露。

[Perplexity Max 官方价格与功能说明](https://www.perplexity.ai/help-center/en/articles/11680686-perplexity-max?utm_source=chatgpt.com)

### 独立判断

这是一个重要的 Agent 产品形态变化：

**Agent 不再只是被调用的 Tool，而开始成为一个持续存在、有记忆、有工作目标、有执行权限的业务参与者。**

但也带来几个关键问题：

1. 多个 Teammate 同时修改同一业务对象，如何保证一致性？
2. Agent 在长期运行中如何管理过期的任务和记忆？
3. 如果 Agent 已经执行了外部操作，如何保证重试不会产生重复交易？
4. 用户如何知道 Agent 过去一周究竟做了哪些事情？
5. Agent 的持续运行成本如何分摊和控制？

我认为这类产品的真正竞争力，不是 Agent 数量，而是长期任务可靠性、权限治理、Memory 和执行审计。

## 2. BrowseSafe++：真实网站上的 Prompt Injection 风险可能远高于静态测试

**论文首次公开：2026-10-12｜公开产品与 Benchmark：2026-11-02｜重要性：A｜领域：Agent Security / Evaluation｜类型：学术 + 开源**

BrowseSafe++ 是由 Perplexity、Purdue University 和 Rutgers University 的研究人员合作提出的 Browser Agent 安全 Benchmark。

[BrowseSafe++ 论文（arXiv）](https://arxiv.org/abs/2610.17457)\
[BrowseSafe++ 官方项目网站](https://browsesafe.perplexity.ai/?utm_source=chatgpt.com)

### 研究问题

Browser Agent 需要读取网页，并根据网页内容执行操作。

问题在于：网页内容不是可信指令。

攻击者可以在普通网页、论坛、共享文档、代码仓库中插入恶意内容，让 Agent：

- 改变用户原本的任务。
- 泄露敏感数据。
- 执行用户没有授权的操作。
- 将恶意指令误认为系统或开发者指令。
- 将伪造的用户偏好当作真实用户要求。

过去的检测方式经常使用明显的恶意指令，例如要求 Agent 忽略之前的指令。

但真实攻击越来越善于伪装成正常页面内容。

### Benchmark 的技术贡献

BrowseSafe++ 将原有 BrowseSafe 从 14,719 个页面扩展为 **38,675 对攻击页面和正常页面**。

其中：

- 32,187 对来自真实网站中观察到的攻击。
- 6,488 对来自原始 BrowseSafe。
- 每个页面提供 HTML、Markdown、Accessibility Tree 和 Screenshot 四种表示。
- 覆盖 12 类网站、24 种攻击类型和 18 种页面位置。

其重要设计是采用匹配的攻击页面与正常页面：

同一个网页，只改变其中的攻击内容，其他正常页面内容保持一致。

这样可以避免检测模型仅仅根据网页主题、布局或来源判断是否存在攻击。[arXiv](https://arxiv.org/html/2610.17457v1)

### BrowseSafe-Guard

研究人员使用 Qwen3.5-0.8B 微调两种轻量检测器：

- Text Detector：检测 HTML、Markdown 和 Accessibility Tree。
- Multimodal Detector：直接读取网页截图。

论文报告：

| 测试场景                          | F1          | False Positive Rate |
| ----------------------------- | ----------- | ------------------- |
| HTML Text Detector            | 98.29       | 1.35%–7.40% 区间内的最低值 |
| Markdown / Accessibility Tree | 92.98–93.26 | 1.35%–7.40% 区间内     |
| Screenshot Detector           | 93.32       | 6.08%               |

论文还报告，在其测试设置中，Text Detector 每检测 1,000 个页面的推理成本约为 0.18 美元，而被比较的 Frontier Models 约为 18.95—180.61 美元。

需要强调：这些是论文作者实验和成本估算，不是第三方独立复现。[arXiv](https://arxiv.org/html/2610.17457v1)

### 更值得警惕的实验：自适应攻击

论文还研究了 BrowseSafe-Adapt。

它不是简单重复已经知道的攻击，而是：

1. 向目标 Agent 投放原始攻击。
2. 观察 Agent 的行为。
3. 根据攻击结果修改恶意指令。
4. 再次尝试。
5. 直到攻击成功或达到尝试次数上限。

在 1,024 个任务上，每个目标最多尝试 64 次。

| 目标 Agent        | 原始攻击成功率 | 自适应攻击成功率 |
| --------------- | ------- | -------- |
| Claude Sonnet 5 | 2.05%   | 30.66%   |
| GPT-5.5         | 0.49%   | 65.23%   |
| Gemini 3.1 Pro  | 2.93%   | 92.87%   |
| DeepSeek V3.1   | 2.93%   | 95.02%   |
| Kimi K2         | 0.59%   | 95.41%   |

这意味着，仅用固定攻击字符串做安全测试，可能严重低估 Agent 在真实环境中的风险。[arXiv](https://arxiv.org/html/2610.17457v1)

### 开源和成熟度

- 论文状态：arXiv 预印本，尚不能视为同行评审后的正式会议论文。
- Dataset：公开。
- SDK：公开，MIT License。
- GitHub SDK：目前页面显示 3 次提交，说明实现仍处于早期阶段。
- 公开 Leaderboard：已有。

[BrowseSafe++ GitHub SDK](https://github.com/perplexityai/browsesafe-plus-plus)

### 独立判断

这是本日最值得深入阅读的学术成果。

它揭示了 Agent 安全的一条重要规律：

**检测到恶意指令，不代表 Agent 不会执行恶意指令。**

因此企业 Agent 安全不能只依赖 Prompt Filter。

真正需要的是：

- Tool Permission Boundary。
- Untrusted Content Isolation。
- Action Policy Enforcement。
- Sensitive Operation Approval。
- Execution Sandbox。
- Trace 和 Replay。
- State-changing Action Verification。

未来值得关注的研究方向是：从 Prompt Injection Detection 发展到完整的 Agent Action Security。

## 3. Supermicro + IBM + NVIDIA：KV Cache 开始进入共享企业存储层

**发布日期：2026-11-05｜重要性：A｜领域：AI Infrastructure / AI Storage｜类型：产品与架构发布**

Supermicro、IBM 和 NVIDIA 联合推出 KV Cache Storage Solution。

[Supermicro 官方发布公告](https://ir.supermicro.com/news/news-details/2026/Supermicro-Launches-KV-Cache-Solution-with-IBM-and-NVIDIA-Demonstrating-Significant-Inference-Performance-Benefits/default.aspx?utm_source=chatgpt.com)\
[IBM Redbook 技术方案《Context Without Limits》](https://redbooks.ibm.com/docs/MD260021/MD260021.html?utm_source=chatgpt.com)

### 架构组成

| 层次                | 产品 / 技术                    | 职责                 |
| ----------------- | -------------------------- | ------------------ |
| Inference Runtime | NVIDIA Dynamo              | 分布式推理与 KV Cache 管理 |
| KV Cache Transfer | NIXL                       | KV Block 数据传输      |
| Shared Storage    | IBM Storage Scale ECE      | 提供持久化共享存储          |
| Storage Server    | Supermicro Petascale       | 提供 NVMe 存储节点       |
| Network           | NVIDIA Spectrum-X Ethernet | 提供高速网络连接           |
| Network Offload   | NVIDIA BlueField-3         | 卸载网络和数据移动任务        |

其关键思想是：不要把所有 KV Cache 都留在昂贵的 GPU HBM 中。

### NVIDIA 的 KV Cache 分层

可以把它理解为一个分层存储体系：

| 层级   | 存储介质                      | 主要用途                |
| ---- | ------------------------- | ------------------- |
| G1   | GPU HBM                   | 当前推理使用的热 KV         |
| G2   | System DRAM               | 超出 GPU HBM 的缓存      |
| G3   | Local NVMe                | 单机更大容量的 Warm Cache  |
| G3.5 | NVIDIA CMX                | Pod 级共享 Flash Cache |
| G4   | Enterprise Shared Storage | 大规模、长期持久化的 KV Cache |

G4 的价值是：跨 GPU 节点共享 KV Cache，并且可以保存更长时间。

对于多轮 Agent、Coding Agent 和 Long-context RAG，这比单纯扩大 GPU 显存具有不同的经济意义。[IBM Redbooks](https://redbooks.ibm.com/docs/MD260021/MD260021.html)

### 性能测试：必须看完整测试条件

IBM Redbook 披露的测试环境：

- 8 个 Supermicro Petascale Storage Nodes。
- 8+2P Erasure Coding。
- 3 台 NVIDIA Spectrum-X SN5600 Switch。
- 4 张 NVIDIA RTX PRO 6000 Blackwell GPU 的客户端节点。
- 模型：GPT-OSS-120B，MXFP4。
- 推理：NVIDIA Dynamo v0.9.0 + vLLM v0.14.1。
- KV Cache：FP16。
- Storage：IBM Storage Scale ECE v6.0.0.1。

模型可以在单张 RTX PRO 6000 Blackwell GPU 上运行，是因为使用了 MXFP4 预量化权重。[IBM Redbooks](https://redbooks.ibm.com/docs/MD260021/MD260021.html)

测试结果：

| 指标               | 无 KV Cache | G4 KV Cache |
| ---------------- | ---------- | ----------- |
| 130K Tokens TTFT | 32.14 秒    | 约 0.57 秒    |
| 200 Requests RPS | 0.19       | 4.26        |
| 200 Requests 总耗时 | 1,048 秒    | 46.94 秒     |

在 Noisy Neighbor 测试中，4 个并发客户端制造 200 GB/s 的竞争网络流量，G4 仍达到 3.6 RPS，约为无 Cache 基线的 18 倍。[IBM Redbooks](https://redbooks.ibm.com/docs/MD260021/MD260021.html)

### 一个容易忽略的技术细节

虽然 Supermicro 服务器支持 GPUDirect Storage，但 Redbook 描述的 KV Cache 读取路径实际是：

**Remote-to-Host（R2H）→ Host-to-Device（H2D）**

即先进入 CPU RAM，再进入 GPU。

因此不能简单将其理解为测试已经证明了完全绕过 CPU 的 GPU-to-Storage 直连路径。硬件具备 GDS 能力，不等于本次所有测试都使用了 GDS。[IBM Redbooks](https://redbooks.ibm.com/docs/MD260021/MD260021.html)

另外，22 倍吞吐提升的测试包含 Cache 从空状态逐渐积累命中率的过程，并非预热后的理想状态。这个区别值得保留。

### 独立判断

这条进展值得 AI Storage 和 Database × Storage 领域重点跟踪。

未来推理系统的数据路径可能变成：

GPU HBM → DRAM → Local NVMe → Shared Flash → Enterprise Storage。

真正需要研究的问题：

1. KV Cache Block 的全局索引与寻址。
2. Cache Invalidation 和版本一致性。
3. 多租户 Cache 隔离。
4. Agent Session 的 KV Cache 生命周期。
5. Cache Hit Rate 与 GPU 利用率之间的关系。
6. G4 存储成本与重新计算成本的经济平衡。

当前测试是厂商联合验证，不是第三方独立 Benchmark；还需要不同模型、不同推理引擎和不同网络拓扑的复现。

## 4. firmly：Agentic Commerce 开始从商品推荐走向真实交易基础设施

**发布日期：2026-11-05｜重要性：A｜领域：AI 应用 / Agent / 商业化｜类型：创业公司融资与产品发布**

firmly 宣布完成 1,500 万美元 Series A，并推出 Ask Agent。

[firmly 官方融资和产品公告](https://www.firmly.ai/blog/series-a?utm_source=chatgpt.com)

### 公司解决的问题

当消费者开始使用 AI Agent 购物，商家会遇到一个新的基础设施问题：

每增加一个 AI 购物入口，商家就需要处理商品目录、实时价格、库存、支付和 Checkout 集成。

firmly 希望通过一套统一的商户接入基础设施解决这个问题。

### 两个产品

**firmly Connect**

面向商户和 AI 平台：

- 连接现有 Ecommerce 系统。
- 统一商品目录和库存访问。
- 提供支付与交易能力。
- 接入不同 AI Agent、Marketplace 和 Social Platform。
- 商户仍然是 Merchant of Record，保留支付渠道和客户关系。

**Ask Agent**

面向消费者：

- 自然语言描述购物需求。
- 查询商户实时商品目录。
- 结合价格、库存和商户政策推荐商品。
- 进入商户自己的 Checkout 流程。
- 支持订单状态和 Loyalty 等能力。 [firmly](https://www.firmly.ai/blog/series-a)

### 商业化证据

firmly 官方披露已有三个实际使用案例：

- Furniture.com：多商户购物车与 Checkout。
- Wizard：AI Shopping Platform，支持实时商品目录和对话内 Checkout。
- RetailMeNot：品牌化商业交易。

公司称其 Connect 网络覆盖超过 1,100 万商户、代表超过 9,000 亿美元 GMV。

需要特别区分：这两个数字是平台可连接的商户和 GMV 规模宣传，不等于所有商户已经实际完成 Agent 交易。[firmly](https://www.firmly.ai/blog/series-a)

### 融资背景

本轮由 Squarepoint Capital 领投，J.P. Morgan Payments、Mastercard、Samsung NEXT 等参与。

融资金额为 1,500 万美元，属于 Series A。[GlobeNewswire](https://www.globenewswire.com/news-release/2026/11/05/3396499/0/en/firmly-raises-15-million-series-a-and-launches-ask-agent-to-help-merchants-more-easily-adopt-agentic-commerce.html)

### 独立判断

firmly 值得关注的原因是，它选择的不是简单的 Browser Agent 路线。

它试图通过商户后端系统和交易协议接入，实现更可靠的交易。

这揭示了 Agentic Commerce 的核心竞争要素：

- Product Catalog。
- Inventory。
- Pricing。
- Payment。
- Checkout。
- Order Management。
- Merchant Identity。
- Transaction Authorization。

**Agentic Commerce 的护城河很可能不是更聪明的购物模型，而是商户、支付、交易协议和履约体系的连接能力。**

下一步应验证真实交易量、交易成功率、商户付费方式和渠道获客成本。目前公开资料尚未提供收入、Take Rate 和实际 GMV 的独立审计数据。

### 独立判断

这不应简单理解为 Google 放弃 Coding Agent。

更合理的解读是：

**Google 正在减少独立 Agent 产品之间的重复建设，把异步执行能力整合进更完整的 Agent 开发平台。**

但这也说明 Agent 产品面临一个现实问题：

用户真正需要的是稳定、可持续的工作能力，而不是越来越多相互独立的 Agent 产品。

这对 Agent 创业公司有三个启示：

1. 不要只靠单一 Agent UI 建立产品壁垒。
2. 用户的 Memory、Workflow 和执行历史必须可迁移。
3. Agent 产品应避免将用户的工作状态完全锁定在单一平台。

# 四、今日产业与学术判断

## 趋势 1：长期运行的 Agent 需要 Durable State，而不是聊天历史

Perplexity Teammates 和 TencentDB Agent Memory 都在解决同一类问题：

Agent 需要跨 Session 记住目标、历史任务、用户反馈、工作文件和业务规则。

未来 Agent 的持久化状态不仅包含 Memory，还包含：

- Task State。
- Workflow State。
- Tool Execution History。
- Approval History。
- Business Object Version。
- Checkpoint。
- Execution Trace。

这意味着 Agent Memory Database 需要从简单的向量检索走向真正的状态管理。

## 趋势 2：Agent 安全必须从 Prompt 防御走向执行边界控制

BrowseSafe++ 的研究说明，攻击者可以根据 Agent 的反应不断修改恶意内容。

这使得单纯依赖 Prompt Filter 和内容检测并不充分。

企业 Agent 的安全模型必须包含：

- Untrusted Data Isolation。
- Tool Call Verification。
- Least Privilege。
- Transaction Boundary。
- Human Approval。
- Audit Trail。
- Action Rollback。

这也意味着 Agent Security 有机会成为独立的企业软件类别。

## 趋势 3：AI Storage 的价值正在从存储模型文件转向存储推理状态

KV Cache 持久化的意义在于减少重复计算。

未来存储系统可能需要管理：

- KV Cache。
- Agent Memory。
- Context Snapshot。
- Session State。
- Model State。
- Long-running Workflow Checkpoint。

数据库、对象存储、文件系统和分布式缓存之间的边界会进一步模糊。

## 趋势 4：Agent 商业化的核心竞争力是业务系统接入

firmly 说明，Agentic Commerce 不能只解决商品推荐。

真正的业务价值在于：

商品 → 库存 → 价格 → 支付 → 交易 → 订单 → 售后。

这同样适用于金融、制造、法律和企业运营 Agent。

谁能真正连接业务系统、控制执行权限，并对交易结果负责，谁就更有机会建立商业壁垒。

## 今日最终判断

今天最值得持续研究的是三个问题：

**第一，Agent 的长期工作状态究竟应该由谁管理？**

是 Agent Framework 自己管理，还是独立 Memory Database、Workflow Engine 和 State Store 共同管理？Perplexity 和 TencentDB Agent Memory 正在从不同层面回答这个问题。

**第二，Agent Security 是否需要独立于模型的执行安全层？**

BrowseSafe++ 说明模型识别恶意指令的能力与实际安全执行之间仍有很大差距。未来企业 Agent 的安全能力，可能更多取决于权限、事务和执行边界，而不是模型本身。

**第三，KV Cache 是否会成为新的共享存储类别？**

如果 Agent 工作流越来越长，跨 Session、跨 GPU 节点的 KV Cache 复用将具有直接的成本价值。G4 共享存储层值得继续跟踪，但还需要验证多模型、多 GPU 和真实多租户环境下的 TCO。

**今天的总体趋势：Agent 正在从“会调用工具的模型”，演进为“拥有持久状态、能够持续执行、可以被治理和审计的业务系统”。**

# AI × Data × Storage 产业与技术雷达

**日期：2026 年 11 月 9 日**\

## 一、今日最值得关注的 5 条进展

### 1. MCP Gateway：Agent 工具访问开始出现独立的基础设施层

**重要性：A｜学术＋生产系统｜论文 v2：11 月 2 日；已录用 ACM SIGOPS ATC 2026**

MCP Gateway 是由 Alibaba Cloud、南京大学 等机构团队研究的 MCP Gateway 系统。它针对企业 Agent 接入大量工具时出现的几个实际问题：

- 工具数量过多，全部放进 Agent Context 会造成上下文膨胀。
- 不同工具接口和协议不一致，传统 OpenAPI 服务不能直接作为 MCP 工具使用。
- 工具检索、权限控制、会话状态和工具调用链路分散在各个 Agent 应用中。
- 工具选择耗时和 Token 消耗会随工具目录规模快速增加。

**核心架构：**

1. **Protocol Adaptation**：将传统 OpenAPI 服务适配为 MCP 工具。
2. **Identity and Access Control**：在 Gateway 层进行身份映射和工具访问控制。
3. **Hybrid Tool Retrieval**：结合语义检索、BM25 和融合排序，避免向 Agent 暴露完整工具目录。
4. **Knowledge Cache**：补充工具调用所需的上下文和前置知识。
5. **Session-aware Routing**：支持会话关联和跨实例路由。

论文披露的部署情况是：系统已在阿里云生产环境运行约 11 个月，覆盖 5 个以上区域，服务数万个 Gateway 实例，接入 315 个云产品、超过 20,000 个 OpenAPI 操作。这是作者披露的生产部署数据，不是第三方审计结果。

**实验结果：**

在包含 3,616 个工具的测试目录中：

- Hybrid Retrieval 的 Recall\@15 达到约 98%。
- 使用 Qwen3-Plus 时，工具选择耗时从 55.7 秒下降至 6.2 秒。
- 对应工具选择阶段的 Token 消耗从约 505.86K 降至 21.22K，约减少 23.8 倍。
- 论文还报告了更低的 P95 工具选择延迟。

这里有一个重要口径：这些数字衡量的是**工具选择阶段**，不是整个 Agent 任务的端到端完成时间。实验结果也属于作者报告，尚不能视为第三方复现。[arXiv](https://arxiv.org/abs/2607.15593?utm_source=chatgpt.com)

**成熟度与局限：**

- 论文已录用 ATC 2026，会议尚未举行。
- 论文描述了生产部署，但未见公开的完整开源实现或可复现 Artifact。
- 会话状态管理引入额外开销；凭据隔离、轮换等安全问题仍需要进一步完善。
- 目前没有公开的独立跨厂商对比测试。

**竞品与判断：**

可以与 Amazon Bedrock AgentCore Gateway、Microsoft MCP Gateway、Kong MCP Gateway、agentgateway、ToolHive 等方向对比。

我认为最重要的不是它做了一个 MCP Proxy，而是它证明了一个值得独立发展的基础设施层：

**Agent Tool Plane：统一工具发现、协议适配、授权、路由、审计和会话管理。**

未来企业 Agent 不应该由每个应用自己维护数百个 MCP Server 和工具权限，而应当像访问数据库、API Gateway 一样访问统一的工具基础设施。这是 Agent Platform 从应用编排走向企业级基础设施的重要变化。

### 5. Supermicro、IBM、NVIDIA 推出共享存储 KV Cache 方案：推理缓存开始进入企业存储层

**重要性：A｜AI × Storage＋AI Infrastructure｜发布：11 月 5 日**

Supermicro、IBM 和 NVIDIA 联合展示了面向 LLM 推理的分层 KV Cache 存储架构。

核心方向是把 KV Cache 从 GPU HBM、DRAM 和本地 NVMe 扩展到共享企业存储：

- G1：GPU HBM。
- G2：主机 DRAM。
- G3：本地 NVMe。
- G3.5：共享缓存层。
- G4：企业级共享存储，采用 IBM Storage Scale。

技术栈包括 NVIDIA Dynamo、vLLM、IBM Storage Scale ECE、Spectrum-X 网络和 Supermicro Petascale 存储节点。[Super Micro Computer](https://ir.supermicro.com/news/news-details/2026/Supermicro-Launches-KV-Cache-Solution-with-IBM-and-NVIDIA-Demonstrating-Significant-Inference-Performance-Benefits/default.aspx?utm_source=chatgpt.com)

**测试配置：**

- 8 个存储节点。
- 16 块 Micron E3 7.68TB NVMe SSD。
- 3 台 400Gb/s Spectrum-X 交换机。
- 推理节点使用 4 张 RTX PRO 6000 GPU。
- 模型为 gpt-oss-120b MXFP4。
- 使用 vLLM 0.14.1、NVIDIA Dynamo 0.9.0 和 Storage Scale ECE 6.0.0.1。
- 200 个请求、28 并发、100 条 Prompt，总计约 2,400 万 Token，KV Cache 规模约 825GB。

**厂商联合测试结果：**

- 在 130K Token Context 条件下，TTFT 最多提升约 56 倍。
- 吞吐从约 0.19 RPS 提升至 4.26 RPS，约 22 倍。
- 在 200GB/s 的共享存储竞争流量下，仍报告约 18 倍吞吐提升。

这里有一个特别重要的测试条件：**测试中关闭了 G1 和 G2，主要验证的是 G4 共享存储层。** 因此不能将结果直接理解为完整五层缓存架构已经在所有层次上实现了这些性能。测试也是联合厂商基准，不是第三方独立复现。[IBM Redbooks](https://www.redbooks.ibm.com/docs/MD260021/MD260021.html)

**独立判断：**

这条路线值得重点研究，因为它将 KV Cache 从单机推理优化问题，进一步变成跨 GPU、节点和集群的共享数据层问题。

它与 NVIDIA Dynamo、LMCache、Mooncake 等方向有相同的架构趋势，但具体差异在于把企业级共享存储作为更深层的 KV Cache Tier。

下一步真正要验证的不是峰值吞吐，而是：

1. Cache 命中率、失效和恢复机制。
2. 多租户并发下的隔离和 QoS。
3. 存储网络拥塞时 GPU 等待时间。
4. 共享缓存的成本与 GPU 重新计算成本之间的平衡。
5. 真实长上下文、Agent 多轮会话和多模型工作负载下的表现。

## 二、今日产业与学术判断

### 趋势 1：Agent 正在从“应用框架”走向独立的数据与工具基础设施

MCP Gateway、Redis Iris、MariaDB Agent Memory、MobileWork 指向同一个变化：

Agent 不再只是一个调用 LLM 和工具的应用，而是需要独立的：

- Tool Plane；
- Context Plane；
- Memory Plane；
- Identity and Policy Plane；
- Execution and Observability Plane。

其中 Tool Plane 和 Context Plane 已经出现比较清晰的产品形态。真正的竞争将集中在权限、审计、状态持久化、执行可靠性和跨 Agent 共享。

### 趋势 2：数据库厂商开始把“业务语义”作为 AI 数据基础设施的核心

Panwei V4.0 和 KES AI 都把语义层作为重要能力。

原因是 Text-to-SQL 和 Data Agent 的瓶颈越来越不是 SQL 语法生成，而是：

- 表和字段的真实业务含义；
- 指标口径；
- 数据权限；
- 多表关系；
- 企业业务规则；
- 数据变化后语义是否同步更新。

未来数据库可能不仅存储数据，也维护供 Agent 使用的机器可理解语义。

但必须验证语义层是否真正进入数据库元数据和权限系统，而不是另建一套知识库。

### 趋势 3：KV Cache 正在成为共享存储系统的新工作负载

Supermicro/IBM/NVIDIA 的方案说明，KV Cache 不再只是 GPU 内存优化。

它可能演进成跨 GPU、CPU、DRAM、NVMe 和共享存储的分层数据服务。未来竞争将从单次推理延迟，扩展到：

- Cache 复用率；
- 跨实例共享；
- 多租户隔离；
- 故障恢复；
- 总体推理成本。

这会给 AI Storage、对象存储和企业存储系统带来新的产品机会。

### 趋势 4：Agent Memory 的研究重点开始从“存进去、取出来”转向“是否真正被使用”

本周值得关注的论文 MemUse 正好说明这一点：记忆系统检索出内容，不代表 Agent 使用了它；Agent 使用了内容，也不代表它改善了任务结果。

这将推动 Agent Memory 的 Evaluation 从 Recall、QA Accuracy 和最终成功率，进一步走向轨迹级因果归因和实际行为分析。

### 3. Agent 安全、治理和商业化

本周观察到的主要变化：

- MobileWork 强调 TraaS 和组织级运营控制，但权限模型、人工审批和回滚机制还需要更多技术文档。
- MCP Gateway 把工具授权和访问控制放在 Gateway 层，是企业治理的重要方向，但凭据隔离仍是需要继续解决的问题。
- Redis Iris 将 Memory、Context、Tool Routing 和 Trace 组合成产品。
- MariaDB 将 Agent Memory、Semantic Cache 和 AI Retrieval 引入数据库平台。

**判断：Agent 安全的竞争重点将从 Prompt Guardrails 转向执行边界。** 未来企业需要知道 Agent 以谁的身份、在什么权限下、通过哪个工具、对哪些数据执行了什么操作，以及失败后如何恢复。

## 四、学术研究与会议雷达

### 1. MemUse：评估 Agent 是否真正使用了持久化记忆

**论文：** *Delivered, Not Used: Evaluating Agent Memory at Its Point of Use*\
**日期：** 2026 年 11 月 1 日\
**状态：** arXiv 预印本，尚未确认同行评审录用。

论文提出 MemUse，分析 Agent 在执行过程中实际收到的记忆内容，并追踪后续行为，区分：

- 记忆是否相关；
- 记忆是否准确；
- 记忆是否提供了新信息；
- Agent 是否实际使用；
- 使用后产生了什么效果。

作者在 8,000 个 SWE-bench Verified 执行 Episode 上评估了 MemGovern、Mem0 和 TencentDB Agent Memory 三种系统。

**核心发现：**

- 三种记忆系统的任务解决率与无记忆基线相差不超过 0.4 个百分点。
- 51%—80% 的相关记忆条目没有被 Agent 实际使用。
- 有益记忆的使用并不保证任务最终成功。
- 有害记忆的使用也不必然导致任务最终失败。

这里最重要的不是“Memory 无效”，而是**最终任务成功率无法解释记忆在执行过程中究竟发挥了什么作用**。[arXiv](https://arxiv.org/abs/2611.01718)

论文还直接评估了 TencentDB Agent Memory，这让它对国内 Agent Memory 产品具有参考价值。

\*\*局限：\*\*研究仍是单一 SWE-bench 任务族上的观察性评估，依赖 Agentic Judge 进行行为归因；不能据此推断所有 Agent Memory 产品的生产效果。当前 arXiv 页面未见公开代码链接。

论文：[MemUse arXiv 全文](https://arxiv.org/abs/2611.01718)

### 2. WAREX：Web Agent Reliability Evaluation

NeurIPS 2026 的 Machine Learning Reproducibility Challenge（MLRC）于 11 月 4 日公布 16 篇入选论文，其中包括：

*WAREX: Web Agent Reliability Evaluation on Existing Benchmarks*

该工作已先被 Transactions on Machine Learning Research（TMLR）接收，再经过 MLRC 的适配审核进入 NeurIPS 2026。它研究的是 Web Agent 在网络错误、页面异常和其他真实执行问题下的可靠性，而不是只在理想环境中比较成功率。[NeurIPS Blog](https://blog.neurips.cc/2026/11/04/mlrc-2026-announcing-the-accepted-papers/?utm_source=chatgpt.com)

这条研究路线值得关注，因为 Agent 的实际任务失败经常不是模型不会推理，而是：

- 页面加载失败；
- 网络超时；
- 页面结构变化；
- 工具执行异常；
- 异常状态没有正确恢复。

这类问题应当进入 Agent Benchmark，而不能只看静态任务成功率。

论文：[WAREX TMLR/OpenReview 页面](https://openreview.net/pdf?id=o4pXVP8RCD)

## 八、观察盲区与证据限制

1. \*\*中国数据库厂商：\*\*本轮重点核验了磐维 V4.0 和 KES AI 数据库。其他国内主要厂商没有发现足以进入本日重点榜单的近 7 日公开产品发布；不能据此判断其没有技术进展。
2. \*\*商业化：\*\*MobileWork 的 30 万用户是中国移动内部推广口径；Redis 和 MariaDB 没有披露 Agent 功能带来的独立收入或 ROI。
3. \*\*性能：\*\*KES 的向量检索数据、磐维的 Token 降低数据，以及 Supermicro/IBM/NVIDIA 的 KV Cache 数据，都需要更完整的测试条件和独立复现。
4. \*\*学术研究：\*\*MCP Gateway 已录用 ATC 2026；MemUse 仍是预印本；WAREX 已经通过 TMLR 审稿并进入 NeurIPS MLRC。三者的学术状态不能混为一谈。
5. \*\*应用层和 Data Engineering：\*\*本轮没有发现足够可靠的新垂直 AI SaaS、BI、ETL/ELT 或数据治理产品发布，因此没有为凑足 5 条而加入低价值新闻。
6. \*\*创业融资：\*\*本轮没有找到足以确认的新一轮 AI Database、Agent Memory 或 Data Agent 融资和并购事件。

\*\*今日总体结论：\*\*最值得持续追踪的是 Agent 的三层基础设施——Tool Gateway、Context/Memory 和可靠执行 Runtime；国产数据库则正在尝试把业务语义和 Agent 数据访问能力纳入数据库产品本身。接下来真正有区分度的证据，将是可复现的系统性能、明确的权限与执行边界，以及外部客户持续付费，而不是更多产品命名和概念发布。
