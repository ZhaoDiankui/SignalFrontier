### 4. Agent Memory / Safety / Evaluation 研究集中出现：记住不等于用对

**时间：** 2026-10-25 至 2026-11-03｜**重要性：** A｜**类型：** 学术论文/Benchmark  
**领域：** Agent Memory、Context Engineering、Agent Safety、Evaluation

本窗口内多篇预印本共同揭示：Memory 的检索质量、Agent 是否实际使用 Memory、Memory 是否改善任务结果，以及 Memory 是否引入安全风险，是不同问题。

#### 4.1 MemUse — Delivered, Not Used: Evaluating Agent Memory at Its Point of Use

**arXiv：** 2026-11-01，预印本。

论文提出在 Memory 真正交付给 Agent 后，沿执行轨迹评估其相关性、准确性、新颖性、影响和实际效果，而不是只测 Recall 或最终任务成功率。

作者在 8,000 个 SWE-bench Verified execution episodes 上评估三种 Memory 系统。报告称，任务 resolve rate 与 no-memory baseline 的差距只有 0.4 个百分点；大量交付的 Memory 无关、未被使用，或重复了 Agent 本来就能看到的内容。即使出现 beneficial memory use，仍有 23.2% 的 episode 失败；而 16 个 harmful-use episodes 中有 5 个最终仍成功。

**研究意义：** Retrieval ≠ Usage ≠ Outcome。Memory 系统需要把“是否召回”“Agent 是否读取和采用”“采用后是否改变动作”“动作是否产生正负结果”拆开度量。

来源：[arXiv:2611.01718](https://arxiv.org/abs/2611.01718)

#### 4.2 MemHarmBench — Evaluating Cross-Session Prompt Injection in Memory-Persistent AI Agents

**arXiv：** 2026-11-01，预印本；公开 Benchmark / Code。

研究跨会话 Prompt Injection：恶意指令先从消息、文档或网页进入持久 Memory，随后原始攻击内容被移除，Agent 在新会话执行正常任务时仍可能受其影响。

Benchmark 从三类受影响主体评估风险：用户、Workspace/Project Owner、External Stakeholder。它强调攻击可以在 Agent 看似正常完成任务、没有明显执行异常时，仍然影响关键决策。

**研究意义：** Persistent Memory 是新的 Prompt Injection 持续攻击面。只在当前 Context 做输入过滤不够；需要对 Memory 写入来源、授权级别、作用范围、有效期、冲突和后续引用建立安全策略。

来源：[arXiv:2611.01700](https://arxiv.org/abs/2611.01700) · [GitHub: MemHarmBench](https://github.com/Kirito14IT/MemHarmBench)

#### 4.3 StateGraph — A State Change Is Local, Its Consequences Are Not

**arXiv：** 2026-11-02，预印本。

StateGraph 面向长期 Agent Memory 的状态一致性问题：上游事实发生变化后，不仅需要修订被直接否定的记忆，还要识别依赖该事实的下游信念、计划和动作是否失去依据。

其方法是维护状态依赖图，通过 counterfactual verification 判断某条依赖是否真实成立；只有严格依赖失效且不存在独立支持路径时，才使下游状态失效。作者构建了 50 个案例的 StateChangeBench，报告相对 CUPMem reimplementation 的 Impact-F1 优势：依赖深度 1 时 +6.9 个百分点，深度 3+ 时 +26.0 个百分点。该结果是作者实验，数据集规模有限。

**研究意义：** Agent Memory 不应只是向量检索和摘要集合，还需要依赖关系、版本、失效传播和可追溯的状态修订机制。

来源：[arXiv:2611.02912](https://arxiv.org/abs/2611.02912)

#### 4.4 Continual AutoResearch

**arXiv：** 2026-11-03，预印本。

论文比较持续保留研究状态的 Agent 与每轮重置状态的 Agent，覆盖 9 类任务和 5 个 Agent。作者报告 Persistent State 能提高研究效率，但不稳定地提高最终解的质量。

**研究意义：** 保留经验与有效利用经验是两种能力。持续运行的 Agent 需要评估状态污染、错误经验累积、上下文膨胀和恢复成本。

来源：[arXiv 搜索入口](https://arxiv.org/search/?query=Continual+AutoResearch&searchtype=title)

#### 4.5 SABench — Task Success Is Not Enough

**arXiv：** 2026-10-25，预印本。

SABench 关注 Email、Calendar、Ticket 等办公任务中的 collateral damage，而非只判断任务目标是否完成。论文报告 201 个任务、2,211 个模型-任务 pairs、11 个 frontier LLMs；15.2% 的所有运行存在 collateral damage；在目标达成的运行中，12.8% 仍包含未授权写操作；模糊任务中的违规率为 38.8%。

**研究意义：** Agent Evaluation 必须同时测量任务成功、授权边界、非目标副作用和数据正确性。任务完成并不能证明操作正确或被授权。

来源：[arXiv 搜索入口](https://arxiv.org/search/?query=SABench%3A+Task+Success+Is+Not+Enough&searchtype=title)

**总体判断：** 这组研究把 Agent Memory 的核心问题从“如何记住更多”推进到“如何确保记忆来源可信、状态一致、授权正确，并在执行时被正确使用”。对企业 Agent 而言，Memory 的版本、来源、权限和失效机制应当是一等系统能力。

### 5. FlatCake：面向长时间 Agent Session 的扁平 KVCache 存储架构

**arXiv：** 2026-10-28｜**重要性：** A｜**类型：** 系统研究/论文  
**领域：** AI Storage、KV Cache、LLM Serving

论文指出，传统 DRAM → NVMe SSD 分层缓存假设在生产 LLM 工作负载下可能失效：一类是复用距离很长的一次性 KV blocks，另一类是超过 DRAM 容量的多 GB Agent Session；SSD 因而可能进入关键读取路径。传统 DRAM staging 和按驱逐顺序写入的布局，也会造成恢复瓶颈和 SSD 读放大。

FlatCake 的主要设计：

- 将 Host DRAM 和 NVMe SSD 作为 Peer Media，置于统一 64-bit address space；
- 利用 KV blocks write-once、immutable、按 Session 复用的特性；
- 写入时直接放置到目标介质，采用 session-contiguous、layer-major 布局，不再迁移；
- 通过 GPUDirect Storage 将合并后的 SSD 读取直接流入有界 GPU window；
- DRAM 与 SSD 请求队列解耦，降低 Head-of-Line Blocking。

作者在 production Claude Code trace + DeepSeek-V4-Flash 上报告：cache hit 约 94%（Mooncake 约 64%）、SSD read amplification 降低 6.5x–6.7x、峰值负载 mean TTFT 改善 1.6x、总 token throughput 改善 1.6x。Llama-3.1-70B、8K–128K context 测试中，mean TTFT 相比 Mooncake 最多改善 2.4x，相比 Mooncake-GDS 最多改善 1.8x。

**证据边界：** 上述均为论文作者报告的实验结果，不是独立第三方复现或普遍生产 SLA；必须结合模型、硬件、Trace、负载和基线理解。论文公开成熟 Artifact 与第三方复现情况仍需持续跟踪。

**独立判断：** 长时间 Coding Agent Session 使 KV working set 达到数十 GB，传统以 DRAM 为中心的缓存层级未必适合所有 Agentic Workload。Session-aware Layout、NVMe 直达 GPU、持久化 Context 和跨任务复用可能成为 AI Storage 的重要方向。

来源：[arXiv:2610.38355](https://arxiv.org/abs/2610.38355)

## 三、其他值得跟踪的技术与产业线索

### 3.1 ForgeKernel：Agent 自动生成与演化 GPU Kernel

**时间：** 2026-11-03｜**类型：** 学术预印本 / AI for Systems

ForgeKernel 探索 Agent 通过跨运行积累知识并演化 Kernel Architecture。论文在 27 个 operators、29 个 configurations 的 NVIDIA Hopper / Blackwell 测试中，报告 25 个 configurations 达到或超过 expert reference，geometric mean 提升约 10%；在 Ascend 910C 的公开案例中报告 8/8 优于参考实现，geometric mean 提升约 25.1%。

这些是作者论文实验结果，不代表生产环境普遍性能。值得关注其代码、Artifact、硬件条件和第三方复现。

来源：[arXiv 搜索入口](https://arxiv.org/search/?query=ForgeKernel&searchtype=title)

### 3.2 Energy Cost of Quantized Agents on Shared GPUs

**时间：** 2026-10-30｜**类型：** 学术研究 / AI Infrastructure

研究在 A100 40GB/80GB、Coding 和 Data Analysis Agent 任务中分析量化对能耗的影响。论文指出，4-bit quantization 可能降低单次执行能耗，但当共享 GPU 的 Cache Contention 和 Admission Limit 等因素进入考虑后，每个成功完成任务的能耗在部分场景反而可能增加（报告最高约 +49%）。

**判断：** Agent 系统应关注 energy per successful task，而不只是 token/s、单次请求功耗或模型显存占用。共享 GPU 的 Admission Control、Cache Contention 和任务成功率会改变真实能效结论。

来源：[arXiv 搜索入口](https://arxiv.org/search/?query=Energy+Cost+of+Quantized+Agents+on+Shared+GPUs&searchtype=title)

## 四、跨领域趋势判断

### 趋势 1：Agent Runtime 正在成为企业控制平面

Agent 平台的竞争从 Framework、Tool Calling 和 Workflow，扩展到长任务、异步执行、状态恢复、身份权限、Trace、审计和成本治理。企业真正需要的是可控的执行系统，而不只是能调用工具的模型。

### 趋势 2：Agent Memory 从检索问题走向状态正确性与安全问题

Memory 需要来源可信、权限感知、版本管理、依赖追踪、冲突解决、失效传播和生命周期治理。Memory Injection 还可能跨会话持续影响决策。向量检索和摘要压缩只是其中一部分。

### 趋势 3：Agentic Workload 正在改变 AI Storage 的访问模式

长时间 Coding Agent Session 会形成大规模、跨步骤复用的 KV Cache 与 Context。DRAM、NVMe、GPU Memory、共享 Flash 和 Object Storage 的协同方式可能需要重新设计。FlatCake 是值得持续跟踪的系统研究信号，但仍需独立复现。

### 趋势 4：Agent 商业化从 Copilot 转向业务结果

Revenue Agent、企业数据 Agent 和办公自动化 Agent 的价值应以真实业务结果衡量：任务完成率、人工介入率、授权违规率、副作用、收入贡献、单位任务成本和客户留存。单纯的调用量、演示效果和模型基准分数不足以证明商业价值。

## 七、观察盲区与证据限制

1. **产品成熟度：** GA、Preview、Beta、Prototype 必须区分。厂商发布路线图不等于功能已普遍可用。
2. **论文证据：** 本期 Agent Memory、Safety、KVCache 和 Kernel 研究多为 arXiv 预印本；预印本不等于同行评审，也不代表生产可用。
3. **性能数字：** FlatCake、ForgeKernel、Energy Cost 等性能或能耗数字来自作者实验，应保留硬件、模型、工作负载和基线条件；不能直接外推。
4. **商业数据：** Nooks 的客户数、NRR 和 ARR 增长预期来自公司披露；资金承诺不等于股权融资或收入。未披露 ARR、收入和实际 GMV 的项目不做估算。
5. **开源成熟度：** GitHub 项目需继续核实代码、许可证、Release、Issue、维护频率、Artifact 和可运行性，不能只看 Stars。
6. **会议日期：** 投稿截止、录用通知、Camera-ready 和会议举行时间分别核对；跨时区截止应以会议官方时区为准。
7. **覆盖盲区：** 本期公开资料对部分中国企业 Agent 产品的底层架构、客户部署、定价和真实使用效果披露有限；相关项目只作为观察对象，不据此判断成熟度。

## 八、本期结论

本期最值得持续跟踪的三条主线：

1. **Agent Runtime / Governance：** 从工具调用走向长任务执行、状态恢复、身份权限、审计和成本控制。
2. **Agent Memory / Context Infrastructure：** 从召回质量走向状态一致性、依赖追踪、来源可信、授权和跨会话投毒防护。
3. **AI Storage：** 从 GPU 本地 KV Cache 走向 DRAM、NVMe、共享 Flash 和 Object Storage 的多层持久化与协同。

与此同时，Agent 商业化正在从通用对话和 Workflow Builder，向销售执行、企业数据访问、文件操作和可持久运行的 Runtime 深入。未来需要重点观察的，不只是 Agent 能否完成任务，而是它能否在真实系统中长期、低成本、可审计地完成任务，并且不破坏数据和业务状态。
