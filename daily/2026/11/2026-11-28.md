## 一、今日最值得关注的 5 条进展

### 1. Linger Desktop 0.1.11 Beta：本地 Agent 开始把模型、记忆、Runtime 和桌面执行打包成个人工作环境

- **发布日期：** 2026-11-27 09:30 UTC（北京时间 17:30）
- **重要性：A**
- **领域/类型：** AI 应用、Agent Runtime、Agent Memory、AI Infrastructure；产品发布 + 开源项目更新
- **项目：** [Linger](https://github.com/simplexai-labs/linger)，由 SimplexAI Labs 维护。GitHub 页面显示约 5.1k Stars、478 Forks、1,220 次提交；这些指标说明关注度和活动度，不代表生产成熟度或用户规模。

**解决的问题与产品形态**

Linger 将个人 Agent 放到用户自己的 Mac/Windows/Linux 电脑上，目标不只是本地聊天，而是让一个常驻 Agent 维护个人 Wiki/Memory、调用其他 Agent Runtime、控制桌面和已登录浏览器，并把长任务放到后台执行。产品组合包括：
- Another Me：主动读取邮件、日历、Slack 等连接器数据，形成 Wiki 页面并按用户反馈调整提醒规则；
- Agent Teams、后台 Task Delegation 和共享模型调度；
- 桌面/浏览器 Computer Use；
- Bring-your-own-runtime：Claude Code、Codex、Pi 等；
- 本地推理引擎 PolyStrata，面向 MoE 模型进行 GPU/RAM/SSD 分层放置。

**本次版本变化**

0.1.11 仍是 **Beta**。本次重点不是单一模型升级，而是 Runtime 与长期任务体验：
- Antigravity Runtime 补齐隔离的 per-Agent runtime home、原生 transcript、Agent Memory、运行中 steer 和上下文用量报告；
- Pi 与 Antigravity 增加后台 idle compaction，减少长期会话上下文膨胀；
- PolyStrata 默认并发从 1 提高到 2，并调整 KV Cache/滑动窗口内存估算；
- 多 Room 并发、桌面安装和 Runtime 探测也有一批工程修复。

**核心架构与性能证据**

PolyStrata 将 MoE 模型中高频使用的 experts 放在 GPU，其他 experts 放在主存或 SSD。Linger README 声称 Qwen3.8-Flash-Next 125B 可在 12GB GPU + 64GB RAM 上运行；项目公布的 RTX 3060 12GB 结果约 45.5 tokens/s，RTX 5090 32GB 约 179 tokens/s。上述数字是项目方自测，尚未看到独立复现；不能解读为“125B 模型只占 12GB 显存”。

**成熟度、许可与商业验证**

- Desktop 0.1.11 Beta；macOS 仅提供 Apple Silicon 桌面包，Windows 安装包仍有 SmartScreen 未签名提示，Linux 要求 glibc 2.35+。
- Linger 仓库使用基于 Apache 2.0、带附加条件的自定义 Linger Open Source License，并非标准 Apache-2.0；若将其作为第三方托管/管理服务提供，需特别核对商业授权条款。PolyStrata 是独立仓库，许可证与 Linger 主仓库不能混为一谈。
- 未披露可核实的融资、付费客户、收入或企业部署规模。零 Token 费用仅适用于本地推理；使用外部模型、语音或连接器仍可能产生第三方费用。

**竞品与独立判断**

与 OpenClaw、n8n Nod、OpenBot 等本地/自托管 Agent 工作区相比，Linger 的差异点是把 MoE 推理引擎、个人 Wiki/Memory、后台 Agent 调度和桌面控制整合到一个产品，而不是要求用户先搭好模型服务再接 Agent。值得跟踪的原因是它把“本地模型”推进到“本地个人 Agent 工作环境”。

主要风险也很清楚：本地运行不等于安全隔离。产品明确允许 Agent 操作用户已登录的 Chrome 和桌面应用；需要进一步审查 Browser/OS 权限、连接器数据出站、后台任务取消、记忆删除和多 Agent 权限边界。当前适合技术试用和架构观察，不宜仅凭“local-first”标签交付高权限账号。

### 2. Anthropic 将 Agent 工作流推进到“可委派任务、途中询问、按策略审批”：MCP 更新与 Claude Ship

- **发布日期：** MCP 更新 2026-11-24；Claude Ship 2026-11-23
- **重要性：A**
- **领域/类型：** Agent Platform、MCP、Agent Safety、AI Coding；产品与开放协议更新

**MCP 更新：Server 不再只是同步工具集合**

Anthropic 宣布：
- Skills over MCP 进入 public beta：MCP Server 可同时发布工具与按需加载的 Skills，把领域知识、操作流程和组织 playbook 与工具一起交付；
- Tasks 与 Elicitation 已 GA：Server 可在后台运行长任务或完整 Agent loop；任务中途可暂停，通过表单或链接向用户请求输入/批准，然后继续；
- File Uploads 扩展即将推出，可把 PDF、表格和图片直接交给 MCP Server，而不是先塞入模型上下文。

官方举例包括 Supabase 在创建付费项目或执行破坏性 SQL 前确认费用/操作、Railway 在删除服务前询问、GitHub 在删除仓库前要求用户明确输入仓库名。Tasks/Elicitation 目前在 Claude 与 Claude Code 的 Pro/Max/Ultra 可用，并向 Team/Enterprise rollout；Skills over MCP 是 public beta，Enterprise 尚待开放。Anthropic 表示这些能力属于开放 MCP spec/extensions，但客户端和 Server 必须分别实现兼容，不能推断所有 MCP Client 已支持。

**Claude Ship：把 PR 生命周期拆成三个 Agent 职责**

Claude Ship 于 11 月 23 日发布，面向 Claude Team/Enterprise 的 GitHub 仓库：
1. Code Review：GA；多角度审查、对发现进行 adversarial verification，再将问题写回 PR；
2. PR Steward：Beta；处理 CI 失败、merge conflict 和 review feedback，但设计上不负责批准或合并 PR；
3. Claude Approvals：Beta；读取仓库中的策略文件，按策略自动批准常规变更，或要求更深层人工审批。

Anthropic 建议先以 observe-only 模式运行，再考虑将审批结果接入 branch protection。支持逐仓库启用、review 深度和 spend limit。计费按 Token 使用量；Claude Ship 暂不支持 Zero Data Retention、HIPAA 配置和 customer-managed encryption keys。

**商业验证与证据边界**

官方列出 TELUS 的正面使用反馈，以及 Carvana 团队的 PR Steward pilot；这属于客户证言/试点，不足以证明广泛生产部署或 ROI。Anthropic 还披露其 Claude Code 团队内部合并 PR 数量增长、revert 比例下降，但这是厂商内部自述，不是独立评测。

**独立判断**

这两项更新共同指向 Agent 协议和产品形态的变化：从一次性 Tool Call，走向可持续运行的任务、途中交互、文件交换和策略审批。对企业 Agent 而言，重要的不只是“能调用工具”，而是任务状态能否持久化、取消/恢复是否可靠、审批是否绑定具体操作与身份、重试是否幂等，以及审计能否还原完整执行轨迹。

MCP 的开放扩展降低了 Server 交付领域能力的门槛，但真正的跨客户端互操作仍需逐项验证 Tasks 生命周期、Elicitation UI、文件权限和认证授权语义。

### 3. 阿里云百炼 Wiki 与本体知识图谱上线：RAG 从 Chunk 增加可编辑的主题知识层

- **发布日期：** 2026-11-24
- **重要性：A**
- **领域/类型：** AI × Data Engineering、RAG、Knowledge Graph、企业 Agent；商业产品功能发布

**解决的问题**

传统 RAG 以 Chunk/向量索引为主要检索单元，适合定位原文片段，但对跨文档主题、实体和概念的组织能力有限。百炼在旗舰版文档知识库中新增 Wiki Page 与本体知识图谱：一次解析同时生成主题知识页面和实体/页面关系视图。

**架构要点**

- Wiki Page 从文档中抽取摘要、实体和概念，形成可阅读、可编辑、可回滚的主题页面，并建立独立索引参与检索；
- 原有 Chunk 检索保留，Wiki 检索与 Chunk 检索并列，问答可同时使用两类检索结果；
- 本体知识图谱由 Wiki Page 关系生成，但**图谱数据本身不参与检索**，主要用于浏览和关系展示。因此不能把该功能直接等同于 GraphRAG 或图查询引擎；
- 可选择 qwen3.8-max、qwen3.8-flash、qwen3.7-plus 作为抽取模型，配置提取粒度、生成要求和实体重点；文档新增/修改后自动更新；
- Wiki Page 支持人工编辑、版本历史和回滚，并可追溯来源文档。

**成本、成熟度与风险**

- 当前仅旗舰版文档知识库支持，标准版不包含。
- Wiki 抽取模型的输入/输出 Token 费用独立于知识库规格费和常规模型调用费用。
- 官方文档给出的非拥堵参考是 500 份文档生成约需 2 小时；受文档大小、模型、平台流量影响，不构成 SLA。
- 一个重要运维语义：关闭 Wiki 不是暂停，会删除全部 Wiki Page、图谱、人工编辑内容和版本历史，且无法恢复；重新开启需要全量生成并再次计费。

**竞品/相关工作与独立判断**

这更接近“生成式知识组织层 + 双索引检索”，而不是完整 GraphRAG：图谱帮助人理解关系，实际召回由 Wiki Page 独立索引和 Chunk 索引完成。它的产品价值在于把企业文档变成可维护、可追溯的主题知识对象，而非只返回一组片段。

建议重点验证：生成页面的事实准确率和覆盖率、跨文档实体合并质量、来源引用是否稳定、文档更新后的增量一致性、删除/回滚语义，以及 Wiki 与 Chunk 结果冲突时的融合策略。对合同、财务、医疗和合规场景，官方也明确建议回看原始文档，不能只依赖生成页面。

### 4. HEAMS：Agent Memory 评测从“答得准不准”扩展到隐私、可删除性、保留策略与投毒防御

- **论文首发：** 2026-11-15，arXiv:2611.20144 v1
- **代码近期活动：** GitHub 仓库在 2026-11-26 仍有更新
- **重要性：A**
- **领域/类型：** Agent Memory、Evaluation、Privacy/Security；学术预印本 + 开源 Benchmark
- **团队：** Mila – Quebec AI Institute Applied Machine Learning Research Team，与 Mozilla 合作；项目说明研究合作由 Mozilla 资助。

**研究问题与贡献**

论文提出 HEAMS（Holistic Evaluation of Agent Memory Systems），核心观点是 Memory 不只是 Agent 的检索组件，而是用户长期信息的 Custodian。Memory 系统需要同时满足五类责任：性能、效率、安全、隐私和用户主权（user sovereignty）。

评测套件由五个既有性能 Benchmark（LoCoMo、LongMemEval、Evo-Memory、BEAM、STALE）、一个既有安全 Benchmark（MPBench）和四个新增评测组成：Contextual Integrity、Transparency、Editability/Erasability、Retention Policy。作者还实现 MilaMem，并提供可包装其他 Memory 系统的 governance layer。比较对象包括 no-memory/in-context、Mem0、Letta、HippoRAG 和 MilaMem。

**实验设置与主要结果**

论文使用统一 Adapter 接口进行评测；Agent 模型为 GPT-5.6-Luna，多个评测由 GPT-4o-mini 作为 LLM Judge。关键结果均为作者在该框架和设置下的实验数据：
- **删除与修改：** 在论文定义的配对探测中，最佳系统 MilaMem 的删除成功率为 47%；所有系统的编辑成功率最高仅 3.66%。这说明“记忆可检索”并不意味着“用户可以可靠地更正或删除记忆”。
- **隐私：** MilaMem 的 Contextual Integrity 场景泄漏率为 57.61%；加入 necessity-gated recall governance 后降至 31.82%。与此同时 Helpful 指标下降 4.80 个百分点，但 Helpful 且无泄漏的比例由 30.86% 升至 45.95%。
- **记忆投毒：** MilaMem 无治理时对 360 次攻击的总体抵抗率为 40%；同时启用 retention 与 recall governance 后升至 88.61%，但仍有 11.39% 的回答受投毒记忆影响。

这些结果说明，检索准确率、任务成功率和 Token 效率不能替代对记忆治理的评估。

**研究局限与可复现性**

- 这是 arXiv 预印本，尚非同行评审论文。
- 评测只覆盖单用户个人对话记忆，不覆盖组织共享记忆、多用户权限、复杂 Tool Use、网页导航或 Computer Use。
- 安全和隐私各只有一个主要 Benchmark；作者承认覆盖深度有限。
- 多数指标使用 LLM Judge，作者尚未用人工标注验证 Judge 的可靠性。
- 统一 Adapter 不能表达所有被测系统的原生能力；论文明确提醒结果描述的是 Adapter 暴露出来的系统行为，不应直接当作各产品的完整排名。
- 外部 Benchmark 被适配到统一执行框架，得分不可直接与原始论文 leaderboard 横向比较。
- 代码为 Apache-2.0；项目自建数据集为 CC BY 4.0，但上游数据集保留原许可证，部分数据集有非商业限制。

**独立判断**

HEAMS 的价值不在于宣布哪个 Memory 产品最好，而是把一组此前经常被忽略的产品契约变成可测指标：记忆能否被审计、能否按用户要求删除/修改、能否遵守保留期限、能否阻止恶意内容进入长期记忆、能否在不同 Agent 间按上下文限制披露。

对 Memory DB 和企业 Agent 平台，值得借鉴的架构结论是：Retention/Recall Governance 应位于 Memory 服务边界，由独立于任务 Agent 的策略层执行；调用 Memory 的 Agent 应视为不可信客户端。下一步应复现 HEAMS，并增加多用户、组织权限、跨 Agent 泄漏、工具注入和在线部署监控测试。

### 5. Cross-GPU Host Memory Timing Channel：GPU 分卡不等于完整的多租户隔离

- **论文首发：** 2026-11-20，arXiv:2611.27115
- **重要性：A**
- **领域/类型：** AI Infrastructure、GPU Cloud、Memory Hierarchy、Security；学术预印本

**研究问题与机制**

论文研究同一物理服务器上的两个租户分别使用不同 GPU 时，能否通过共享主机内存子系统产生跨 GPU 时间侧信道。作者发现，两个 GPU 即使没有 NVLink、共享 IOTLB 或 P2P 访问，仍可能因为 DMA 对 pinned host memory 的访问触发 IOMMU page-table walk，并争用共享 Host DRAM memory controller，导致另一张 GPU 上攻击者自己的内存访问延迟变化。

威胁模型中的攻击者没有 root、性能计数器、Victim API 或 Victim 数据访问权限；可跨进程、Docker container 和 Unix user 边界观察时间信号，但要求双方 Host Memory 流量落到同一个 memory controller。

**实验环境与结果**

作者在两张 RTX 6000 Ada 的工作站、包含 RTX PRO 5000/6000 Blackwell 的双路服务器，以及四张 RTX PRO 6000 Blackwell 的服务器上进行实验。论文报告：
- 合谋的两张 GPU 可用约 20 bit/s 的速率通过该通道传递短秘密；复现实验的原始 BER 在 20–50 bit/s 条件下约为 0–2%；
- 在 CPU-offload 的模型部署中，输出长度推断在干净分段条件下与真实长度的 Spearman 相关系数约 0.95–0.998；端到端在 9 个新 Victim 进程中成功 6 个；
- 对 Qwen2.5-0.5B 的拒答状态推断 balanced accuracy 达 0.955，但在其他模型上结果不稳定，依赖拒答回答比正常回答短这一行为假设；
- **重要反例：** 作者测试的 vLLM + LMCache 7B 场景中，Cache Hit、All Miss 和 Batch 48 的 AUC 分别约 0.497、0.495、0.495，未观察到可用泄漏信号。说明攻击效果强烈依赖持续的 device-to-host DMA footprint，不能泛化为“所有 vLLM/LMCache 部署都可被攻击”。

**局限与安全意义**

这是 arXiv 预印本，尚未同行评审。该侧信道泄露的是活动、输出长度或拒答状态等时间信息，不是直接读取 Victim 输出文本或模型内存。攻击要求共享 Host Memory Controller；真实 LLM 工作负载的请求分段会失败，论文也披露约三分之一的新进程端到端推断失败。论文称原始逐试验数据和分析脚本已归档，但本次未定位到明确的公开 Artifact 仓库链接。

**独立判断**

对 GPU Cloud 和推理 Serving 来说，安全边界不能只按 GPU Device/MIG/vGPU 划分，还要考虑 PCIe、IOMMU、pinned host memory、NUMA 和 memory-controller placement。论文支持的防御方向包括把互不信任的租户放到不同 memory controller，并降低 DMA footprint 的可区分性。对生产服务的实际风险应结合真实模型 offload、KV Cache 迁移和网络/存储路径复测；不能仅凭实验室侧信道就推断云厂商现网已受影响。

**原始来源**
- [arXiv 论文与实验说明](https://arxiv.org/abs/2611.27115)

## 二、今日产业与学术判断

1. **Agent 从 Tool Calling 进入可委派的长任务执行。** MCP Tasks/Elicitation、Claude Ship 的 PR Steward/Approvals、Linger 后台任务都在把 Agent 从“发出工具调用”推进到“交付一个有状态任务”。下一阶段竞争点会落在 durable task state、取消/恢复、幂等、审批绑定、权限传播和 Trace/Replay，而不只是 Planner 能力。

2. **Agent Memory 的主战场正在从 Recall Quality 转向治理契约。** HEAMS 揭示了删除、编辑、隐私披露和投毒抵抗的明显缺口。企业级 Memory 需要把 retention、recall、provenance、version、erase/edit receipt 和跨 Agent access policy 做成服务端强制机制，不能依赖每个 Agent 自觉遵守 Prompt。

3. **企业知识库开始出现 Chunk 与主题知识对象并存的产品形态。** 百炼 Wiki 把模型生成的主题页面作为独立召回单元，同时保留原始 Chunk；图谱当前主要用于浏览，不参与检索。这个方向有产品价值，但必须严格区分生成式知识组织、GraphRAG 和真正的图查询/图检索，尤其要把来源溯源与更新一致性纳入评测。

4. **AI Infrastructure 的隔离边界向 GPU 之外扩展。** Cross-GPU 论文提示 Host DRAM、IOMMU 和 NUMA memory-controller placement 可能成为新的多租户侧信道面。GPU Cloud 的资源调度、模型 Offload、KV Cache 和安全隔离设计需要联合考虑，不能只看显存分区或 GPU 型号。

## 三、Agent 专项观察

- **产品与应用：** Linger Desktop 0.1.11 Beta 是近 24 小时内最明确的 Agent 产品更新；Claude Ship 将代码审查、修复与审批串成 PR 生命周期。
- **平台与 Runtime：** Anthropic MCP Tasks/Elicitation 将长任务和途中审批开放为协议扩展；百炼此前已提供 Managed Agent 沙箱持久化（11 月 8 日更新），本次新增 Wiki 知识层。
- **开发生态与协议：** Skills over MCP public beta；Tasks/Elicitation GA；File Uploads 即将 rollout。兼容性仍需按 MCP Client/Server 组合逐项验证。
- **Memory/Context：** HEAMS 将隐私、遗忘、编辑和投毒防御纳入统一评测；Linger 使用本地 Wiki/Memory，百炼使用可检索 Wiki Page，均说明 Memory/Context 正从向量召回走向有版本、有治理的持久知识层。
- **安全治理：** Claude Ship 采用仓库策略文件和 observe-only；MCP Elicitation 在破坏性操作前要求用户确认；HEAMS 与 Cross-GPU 论文分别揭示 Memory 数据治理和底层硬件共享资源风险。
- **Evaluation/Observability：** HEAMS 是本日最值得加入研究清单的 Memory Benchmark；目前没有发现近 24 小时内新的、具有充分证据的 Agent 全栈 Benchmark 大版本发布。
- **商业化：** Claude Ship 面向 Team/Enterprise、按 Token 计费；百炼 Managed Agent 已商业化计费，Wiki 抽取另按 Token 计费；Linger 尚无可验证客户/收入披露。客户证言、Beta rollout 和实际生产部署必须分开看待。
- **开源项目脉搏：** 本轮还检查了 LangChain、Dify 等种子项目；Dify 1.20.0（11 月 18 日）包含消息渠道 Human-in-the-loop、OpenTelemetry Trace 与文件安全扫描等更新，但不属于本日新增，未挤占重点名额。

## 六、观察盲区与证据限制

1. **Database/Storage 产品发布：** 近 24 小时及近 7 天未发现足以进入前五的、可由一手来源确认的核心数据库内核、云数据库、对象存储或分布式 KV 大版本发布。不能据此推断这些领域没有研发活动。
2. **AI Infrastructure：** 本日最有价值的研究信号是 GPU Host Memory 侧信道；尚未找到同等强度的 GPU Cloud 新商业发布或可独立验证的推理成本/性能突破。
3. **中国市场：** 百炼 Wiki 是本轮确认的主要产品进展；国内其他 Agent/Data/Storage 产品有零散消息，但公开技术细节、价格、客户或可运行材料不足，未为凑数纳入。
4. **学术证据：** HEAMS 与 Cross-GPU Timing Channel 均为 arXiv 预印本，不代表同行评审或生产环境验证。HEAMS 的 LLM Judge 尚未通过人工标注校准；Cross-GPU 侧信道对真实模型的攻击效果依赖持续 DMA footprint 和请求分段条件。
5. **商业化证据：** Claude Ship 的客户引用和 Carvana pilot、百炼的产品功能上线、Linger 的 GitHub 热度，分别属于客户证言/试点、产品可用性、社区关注度，均不能替代付费部署规模、收入和 ROI 证据。
6. **会议论文：** CIDR 2027 Accepted Papers 页面提供录用标题和作者信息，但本轮没有逐篇获取完整论文/Artifact，因此只做议题趋势观察，不对未阅读论文的算法和实验结果作判断。

**本日结论：** 值得持续追踪的主线不是单纯“更强的 Agent 模型”，而是 Agent 任务执行的持久化与审批、Memory 的数据治理、企业知识的可维护表示，以及 GPU/Host Memory 的多租户安全边界。数据库、存储和基础设施仍是这些能力能否安全规模化的底座。
