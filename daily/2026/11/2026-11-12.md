# AI × Data × Storage 产业与技术雷达

2026 年 11 月 12 日｜全球视角｜中文深度简报

本期重点观察三个正在交汇的趋势：数据库开始成为 Agent 的运行时数据基础设施；Agent 从应用框架走向受治理的生产执行环境；KV Cache 正从 GPU 内存管理问题演变为跨 GPU、网络与存储的系统工程问题。

## 一、本期高价值信号

### 1. Neo4j 发布 Relate：面向 Agent 的嵌入式数据库开始成为独立产品形态



已发布 / Apache-2.0

&#x20;2026-11-11



Relate by Neo4j 是本期最值得关注的数据库产品发布之一。它不是把传统 Neo4j 简单包装成 MCP Server，而是提供一个面向 Agent 执行环境的轻量级、进程内数据库：

- Rust 实现，内存优先，可选持久化 WAL。
- 内置 MCP Server、CLI、Bolt 和 HTTP Query API。
- 支持 Cypher、图遍历与向量相似度查询组合。
- 针对 Agent 调用设计结构化错误和可重试标志。
- 对查询结果设置行数上限和截断标记，避免大结果集挤爆上下文窗口。
- 官方称内存读取达到亚毫秒级；这是厂商指标，仍需独立压测。

产业判断： 这代表数据库竞争的一个新切面：不再只是服务应用程序，而是直接嵌入 Agent 的执行环境。Agent 需要低延迟的临时状态、结构化记忆、局部知识图谱，以及能够被工具调用安全消费的查询结果。

需要验证的关键问题：

1. 内存状态与 WAL 的崩溃恢复语义是什么？事务隔离和持久化边界如何定义？
2. 多 Agent 并发访问时，锁竞争、隔离和资源配额如何处理？
3. 嵌入式数据库能否支持 Agent 生命周期结束后的状态迁移、备份和审计？
4. MCP 接口是否只是方便调用，还是具备权限约束、调用审批和操作验证？

对行业的意义： Relate 值得与 SQLite、DuckDB、Kuzu、RocksDB 以及各类 Agent Memory 产品进行对比。它不等于企业数据库的替代品，更像是 Agent 本地运行时的数据层。

### 2. Agent Substrate 1.0 GA：Agent Runtime 开始从框架竞争转向基础设施竞争



GA / CNCF Sandbox

&#x20;2026-11-05 至 11-10



Agent Substrate、kagent 和 gVisor 的组合，正在形成一条相对清晰的 Agent 基础设施路线。

其核心不是再做一个 Agent Framework，而是解决 Agent 大规模运行的资源和安全问题：

- Actor： 保存 Agent 会话状态、文件和身份。
- Worker： 从可复用的 Kubernetes 执行池中分配沙箱。
- Gateway： 控制 Agent 的进出流量、身份和访问策略。
- Agent 空闲时可以快照状态并释放 Worker，需要继续执行时再恢复。

Google 声称恢复时间低于 500ms，能够支持百万级沙箱、约为标准容器运行密度的 10 倍；这些是项目方公布的测试指标，不能直接视为任意工作负载下的性能保证。

11 月 10 日，Solo.io 宣布 Agent Substrate 和 kagent 企业版 GA，并披露 OutSystems、Swissquote 等客户的生产使用情况。Google 11 月 5 日也宣布将 Agent Substrate、gVisor、OpenRL 贡献至 CNCF Sandbox。注意：进入 Sandbox 不等于 CNCF 毕业或项目已经成熟稳定。

产业判断： Agent 生产化的基础设施栈正在成形：

`Agent Framework → Agent Runtime → Sandbox → Identity/Gateway → State & Memory → Observability`

这条路线与传统 Kubernetes 的关系很像：Kubernetes 管理容器和服务，Agent Runtime 还要管理跨多轮任务的会话状态、身份、暂停恢复和工具权限。

值得关注的技术难题： 快照恢复的一致性、外部副作用的恢复语义、跨 Worker 的身份连续性、秘密注入、工具调用审计，以及 Agent 被暂停时事务和长连接如何处理。

### 3. SGLang、vLLM 与存储厂商：KV Cache 正在成为独立的基础设施层

开源版本已发布 / 商业联合方案已发布

本期有两类进展值得放在一起看：

- SGLang 0.5.23（11 月 2 日）增加 DeepSeek 风格 MLA 模型通过 HiCache 文件型 L3 存储使用 Prefix Cache 的能力；还继续推进 CPU 内存 KV Cache、PD 分离和长上下文推理优化。
- vLLM 0.33.0（11 月 2 日）推进低精度 KV Cache，包括 NVFP4，以及更丰富的调度、模型和推理能力。
- Supermicro、IBM、NVIDIA 11 月 5 日发布联合 KV Cache 存储方案：Supermicro 全闪存服务器、IBM Storage Scale、NVIDIA Dynamo 和 Spectrum-X 网络组合。

Supermicro 公布的联合测试称，在 120B 模型、13 万 token 提示场景下，持久化 KV Cache 可带来最高 56 倍 TTFT 改善。这个数字高度依赖基准条件，不能直接推广到其他模型、命中率、并发量和网络拓扑。

产业判断： 推理系统正在出现类似传统存储层次结构的演进：

L0：GPU HBM

当前请求活跃 KV、最高带宽、容量最贵

L1：CPU DRAM

近端缓存、跨请求复用、容量扩展

L2：本地 NVMe / 文件型缓存

持久化或较大容量的缓存层

L3：共享网络存储

跨 GPU 节点共享、容量扩展、恢复与复用

这里真正的竞争点并非简单地“把 KV 放到 SSD”，而是缓存命中、分块索引、前缀一致性、传输开销、淘汰策略、跨节点共享和故障恢复之间的系统优化。

值得跟踪的开源项目： SGLang HiCache、Mooncake、NVIDIA Dynamo、vLLM KV Cache、LMCache。应重点比较它们的缓存管理接口、存储后端抽象、数据布局和跨节点复用能力，而不是只比较单一 TTFT 数字。

### 5. PhoenixAI Contextbase：语义、知识、记忆、Trace 和 Evaluation 合并到一个数据系统



Private Preview

&#x20;2026-11-04



由 StarRocks 创始团队发展而来的 PhoenixAI 发布 Contextbase，定位为 Agent 的 Context Infrastructure。

其核心想法是将以下信息统一存储并关联：

- 语义定义与业务知识；
- 文档与检索数据；
- Agent Memory；
- 执行 Trace；
- 评估结果。

公司认为 Agent 不仅要读取知识，还要知道知识代表什么、过去执行过什么、执行结果如何，以及哪些结果值得信任。Contextbase 计划让这些记录具备版本、治理和可追溯性。

产业判断： 这是本期最值得跟踪的 AI + Database 创业方向之一。它试图把 Agent 的上下文从分散的 Vector DB、Semantic Layer、Memory Service 和 Observability 工具中抽象出来，形成统一的数据底座。

但当前是 Private Preview，暂不能把产品愿景当作已经验证的市场需求。应重点验证其是否真正具备：

1. 统一的数据模型，而非多个产品的集成包装；
2. 语义定义、记忆和 Trace 之间的版本一致性；
3. 低延迟、高并发的在线读取能力；
4. 可迁移、可审计的数据接口；
5. 相较于现有 StarRocks + 向量检索 + Observability 组合的真实增量价值。

### 3. Agent 安全：不只是提示词防护，而是执行边界

企业 Agent 的主要风险不是模型回答错误，而是模型在错误理解、错误上下文或恶意输入下执行了真实操作。

我建议把 Agent 安全分为五个层次：

1. 身份层： Agent、用户、服务账号和子 Agent 的身份不能混淆。
2. 工具层： 工具权限必须最小化，不能仅依赖 Prompt 声明。
3. 数据层： 查询、修改和删除操作要有数据范围与权限边界。
4. 执行层： 高风险动作必须有验证、审批、幂等和补偿机制。
5. 审计层： 保存模型决策、工具输入输出、审批结果和最终副作用。

特别值得注意的是：Agent 的权限不应因为一次用户授权而无限延伸到后续所有子任务。权限应该与任务、资源、操作和时间范围绑定。

### 1. PolyMemDB：面向 Agent Memory 的多模态、多类型数据库系统

arXiv 预印本 / 2026-10-22 修订

论文：PolyMemDB: A Polyglot Database System for AI Memory Management

研究提出面向 Agent 长期记忆的多类型存储架构，覆盖图、向量、概率和时空数据，并使用概率推理机制处理长期事实冲突、时间衰减和数据溯源。

值得研究的点： Agent Memory 不是简单地把对话转成向量。长期记忆至少需要支持事实、事件、关系、时间、置信度和来源。不同记忆类型可能需要不同的存储与查询模型。

局限： 当前材料是预印本及系统演示，不能视为已经通过大规模生产验证。

### 2. Storage Is Not Memory：从“抽取记忆”转向“检索时决定记忆什么”

arXiv 预印本 / 2026-05-06

论文：Storage Is Not Memory: A Retrieval-Centered Architecture for Agent Recall

论文提出一个值得重视的观点：如果在数据写入时就过早压缩、抽取和丢弃信息，后续查询需要的内容可能已经无法恢复。作者主张保留更完整的原始事件，在检索阶段再进行多阶段处理。

论文报告了 LoCoMo、LongMemEval、BEAM-1M 等基准上的实验结果，但这些结果是作者报告，仍需关注数据集、模型、提示词、成本和独立复现条件。

研究启发： 对 Agent Memory 而言，写入策略与读取策略需要分开设计。不能简单地把“记忆抽取准确率”当成最终效果。

这与数据库的 WAL、事件日志、物化视图、索引重建和时间版本管理存在很强的系统设计联系。

## 六、存储、硬件与 AI Infrastructure

### 1. KV Cache 外置存储：从实验性优化走向商业化方案

Supermicro、IBM、NVIDIA 的联合方案表明，KV Cache 正在形成可独立采购、部署和优化的基础设施层。

但这里要区分三种不同的系统需求：

- Cache offload： GPU HBM 不足时，把 KV 状态转移到 CPU 或本地存储。
- Cache sharing： 多个推理实例共享可复用的前缀或 KV 状态。
- Cache persistence： 服务重启、节点故障或请求迁移后，尽可能恢复已有状态。

三者的性能目标和一致性要求并不相同。前者重视传输效率，第二类重视索引和共享协议，第三类重视持久化、校验和恢复语义。

### 2. 存储系统未来值得关注的五个问题

| 方向          | 核心问题                  | 值得研究的技术                 |
| ----------- | --------------------- | ----------------------- |
| KV Cache 分层 | GPU、CPU、NVMe、远端存储如何协同 | SGLang HiCache、Mooncake |
| RDMA / 网络存储 | 如何降低跨节点 KV 传输延迟       | RDMA、RoCE、Spectrum-X    |
| 分布式文件系统     | 元数据如何扩展，如何减少协调开销      | SwitchFS、并行文件系统         |
| CXL / 内存池化  | 如何将内存资源从单机扩展到集群       | CXL Memory、内存池化         |
| 存储能耗        | 如何在性能、功耗和成本之间优化       | 自适应功耗存储服务器              |

本期没有足够的一手证据确认新的 CXL 产品或大规模商业部署，因此不把它包装成近期已落地的产品突破。CXL 仍应作为长期硬件架构跟踪项。

## 八、产业机会与技术判断

### 机会一：Agent 数据访问控制与安全执行

企业不敢让 Agent 操作生产数据库，根本原因不是 SQL 生成能力不足，而是缺乏可信的执行边界。

真正有价值的产品应该把以下能力组合起来：

- SQL / API 操作的静态与动态验证；
- 资源级、行级、列级权限控制；
- 只读优先、变更审批和操作风险分级；
- 事务隔离、幂等、回滚和补偿；
- 执行前后数据一致性校验；
- 全链路审计与可重放 Trace。

这里存在独立于 Agent Framework 的产品机会。它可以成为数据库和 Agent 之间的安全执行层。

### 机会二：Agent Context Database

Neo4j Relate、Redis Iris、PhoenixAI Contextbase、MongoDB Atlas Agent Engine 的产品方向说明，Agent 的上下文正在成为一类独立的数据资产。

真正的产品竞争力不在于支持多少个向量索引，而在于能否统一管理：

- 事实与事件；
- 业务语义；
- 长期记忆；
- 数据来源和版本；
- 执行轨迹；
- 评估结果；
- 权限与生命周期。

未来可能出现类似“Agent Context Database”的产品类别，但目前尚未形成统一技术标准。

### 机会三：Agent Runtime 与数据库状态管理的结合

Agent 是长时间运行、可能中断、可能恢复、可能产生副作用的执行实体。

传统数据库擅长事务与持久化，Kubernetes 擅长容器调度，而 Agent Runtime 需要把两者结合起来。

需要研究的问题包括：

- Agent checkpoint 与数据库事务如何协调？
- Agent 暂停时，未提交事务如何处理？
- Agent 恢复后，如何防止重复执行工具调用？
- 多 Agent 协作如何实现状态隔离？
- Agent 身份、数据库角色和用户授权如何绑定？

这是一条值得长期投入的系统研究路线。

### 机会四：推理 KV Cache 的存储产品化

随着 Agent 多轮推理、长上下文和多 Agent 协作增加，KV Cache 的生命周期会越来越长，跨请求复用的价值也越来越高。

如果能够提供跨推理引擎、跨 GPU 节点、跨存储后端的统一 KV Cache 管理能力，可能形成新的基础设施产品。

但需要注意：KV Cache 与普通 Redis 缓存不同，不能只提供 GET/SET 接口。其核心挑战是模型兼容性、块布局、前缀匹配、版本、传输成本和一致性。

### 本期需要避免的几个误判

1. Agent Memory 项目 Star 数量增长，不代表长期记忆准确率或企业付费需求已经验证。
2. Agent Substrate 进入 1.0，不代表所有 Agent 工作负载都适合快照恢复架构。
3. KV Cache 宣称最高几十倍 TTFT 改善，不代表一般请求也能得到同样收益。
4. 数据库增加 MCP 接口，不代表数据库已经具备 Agent-native 能力。
5. 把语义层、向量检索、记忆和 Trace 集成在一个产品中，不代表它们已经拥有统一的数据一致性和治理模型。

### 本期最终结论

产业正在从“AI 调用数据库”转向“数据库、存储和运行时共同支撑 Agent 自主执行”。

这可能是未来几年 Database × Storage × AI 最值得关注的变化之一。数据库内核、分布式存储、推理缓存和 Agent Runtime 之间的边界会逐步重构，但真正能成为基础设施的产品，必须解决可靠性、数据正确性、权限、成本和可运维性，而不仅仅是提供一个方便的工具接口。
