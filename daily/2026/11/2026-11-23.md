### 1. OpenAI 将 Codex 从“辅助调查”推进到可恢复、可审计的生产工程工作流

- **发布日期：** 2026-11-19
- **重要性：** A
- **领域 / 类型：** AI Agent、AI for Software Engineering、Agent Runtime / Observability / Evaluation；产业实践
- **对象与问题：** OpenAI 工程团队公开介绍 Performance Factory，用 Codex 自动处理 ChatGPT 性能回归：从告警调查、根因分析、修复建议，到部署后验证是否恢复。它针对的不是单次代码生成，而是重复发生、需要跨工具和跨时间推进的工程运维任务。
- **团队与背景：** 文章由 OpenAI 技术团队成员 Okay Zed、Cyrus Forbes 撰写。该系统用于 OpenAI 自身工程环境，**不是对外发布的商业产品**。
- **核心架构：**
  1. **Task service：** 以配置文件定义任务状态、合法状态转换和必须由工程师介入的节点；
  2. **Dispatch loop：** 轮询可执行任务，并在任务进入下一状态时分配 Agent；
  3. **Cloud execution：** Codex 在 OpenAI 内部网络中运行，可访问代码仓库、metrics、logs、traces、CPU profiles 和 memory snapshots；
  4. **Event subscriptions：** 等待 GitHub review comment、CI 失败或部署完成等事件，事件到达后恢复任务，而不是让 Agent 持续轮询或依赖原始对话上下文。
- **关键流程：** 告警触发 → 分析受影响请求和指标变化 → 检查部署、配置与代码 → 独立 Codex 会话进行 adversarial review → 提出修复并创建 PR → 工程师审查、部署 → Agent 再次检查指标是否恢复；若未恢复则重新进入调查。
- **运行证据：** OpenAI 称该 Regression Workflow 在三个多月内跟踪了 **1,700 多次调查**、定位根因 **600 多例**，约每天 17 次自动调查。更重要的是，人工抽查 100 条根因建议时，约 **70% 被评为准确**，另有约 30% 需要进一步完善或未充分证明因果关系。这是作者披露的内部生产数据，不是第三方评测。
- **成熟度与安全边界：** 已在 OpenAI 内部生产使用；任务状态存储在 Agent 上下文之外，并以服务身份运行，便于限制权限和识别 Agent 操作。但**修复仍由工程师审查并决定是否合并、部署**，部署后由 Agent 验证恢复。当前没有公开客户、定价、独立代码仓库或可供外部复现的完整实现。
- **竞品 / 相关工作：** 与 LangGraph、Temporal 等工作流编排思路相比，Performance Factory 的关键不是通用多 Agent 对话，而是围绕性能回归建立领域专用状态机、事件恢复、可观测性工具接入和人工审批闭环。
- **独立判断：** 这是近一周最有价值的 Agent 工程实践之一。它说明长周期 Agent 进入生产的关键设施包括持久任务状态、事件驱动恢复、最小权限服务身份、独立反证审查和部署后验证。70% 的人工抽查准确率也提醒我们：Agent 可以扩大调查吞吐，但不能把“找到一个看似合理的原因”当成根因已被证明。
- **原始资料：** [OpenAI Engineering：How OpenAI’s Performance Factory keeps ChatGPT fast](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast/)

### 2. 持续运行 Agent 与桌面 Computer Use 同时进入更广泛的企业可用阶段，但执行边界差异很大

- **发布日期：** OpenAI Business Standard rollout：2026-11-19；Anthropic Computer Use beta：2026-11-20；OpenAI Dots 帮助文档截至 2026-11-23 已更新
- **重要性：** A
- **领域 / 类型：** AI 应用、Agent 产品、Computer Use、企业治理；产业
- **对象与用户：** OpenAI Dots 面向个人与组织提供持续运行的 Agent；Anthropic 将 Claude Computer Use beta 扩展到 Team 和 Enterprise 组织。两者都在突破“只在聊天窗口回答问题”的产品边界，但不是相同的执行模型。
- **OpenAI Dots：**
  - Dots 是常驻 Agent，可利用自己的 cloud computer 和用户连接的应用，在对话结束后继续推进项目、按计划运行任务并主动通知用户；
  - Dots 已向部分支持地区的 ChatGPT Plus 用户逐步开放，也在向美国符合条件的 Business Standard 成员 rollout；Enterprise、Edu、Healthcare 工作区符合条件时已进入 GA，2026-11-18 起默认开放，管理员可选择退出；
  - Enterprise 定价文档披露：Standard / Advanced / Expert dot 的完整付费月价格分别为 **50 / 200 / 500 美元**；至 2027-01-13 前不收费，2027-01-14 起对启用的 Enterprise dots 计费。Dots 委派给 ChatGPT Work 或 Codex thread 的工作仍按相应规则另行计费。该价格仅针对 Enterprise，不应外推到 Plus 或 Business。
- **Anthropic Computer Use：**
  - 2026-11-20 起，Team 与 Enterprise 计划进入 beta、按组织逐步开放，默认关闭；
  - Claude 可查看用户屏幕，并在获准的桌面应用中点击、输入和导航；桌面端支持 macOS 14+ 与 Windows，web/mobile 远程使用还需要组织开启 Computer access，并连接到运行 Claude Desktop 的电脑；
  - 管理员可限制用户角色、设置 app allowlist / blocklist，并通过 MDM 控制设备。
- **安全与执行边界：** Anthropic 官方设置文档明确说明，Computer Use 与用户应用之间**没有 sandbox**；它不局限于用户此前连接的文件夹，获准应用可能让 Claude 打开、修改或删除这些文件夹以外的文件。截图会随聊天保存。应用 allowlist、逐应用授权和 MDM 能降低风险，但不能等同于进程级沙箱或数据访问边界。
- **成熟度与商业化：** Dots 是分阶段 rollout 与分层计费；Claude Computer Use 仍是 Team / Enterprise beta，尚无单独公开定价。两者均不能仅凭“企业版可用”推断已在大规模生产环境稳定运行。
- **竞品 / 相关工作：** Dots 更接近拥有独立云端执行环境、连接器和持续任务状态的个人/组织 Agent；Claude Computer Use 则强调对真实桌面应用的视觉操作。前者的关键风险在云端委托、连接器权限和任务治理；后者还增加终端屏幕、应用和文件操作的风险面。
- **独立判断：** Agent 产品正分化为“云端持续委托”与“端侧 Computer Use”两条路径。后者尤其需要最小权限、专用账号、低敏感度应用白名单、可回放审计和人工确认；不能把文件夹权限或聊天级审批误认为桌面操作的完整隔离。
- **原始资料：** [OpenAI：Getting started with your dot](https://help.openai.com/en/articles/20001530-getting-started-with-your-dot)；[OpenAI：Dots Enterprise pricing](https://help.openai.com/en/articles/20001641-pricing-and-billing-for-dots-in-chatgpt-enterprise)；[ChatGPT Business release notes](https://help.openai.com/en/articles/11391654-chatgpt-business-release-notes)；[Anthropic：Computer use setup for Team and Enterprise](https://support.claude.com/en/articles/18483812-set-up-computer-use-for-team-and-enterprise-plans)；[Anthropic：Release notes](https://support.claude.com/en/articles/12138966-release-notes)

### 3. Dell 将 Agentic Data Gateway、数据治理与 AI 存储平台打包，争夺企业 Agent 的数据入口

- **发布日期：** 2026-11-16（SC26）
- **重要性：** A
- **领域 / 类型：** AI × Data Engineering、AI Data Platform、AI × Storage、AI Infrastructure；产业产品发布
- **产品与问题：** Dell AI Data Platform 宣布新增数据编排和存储引擎能力，目标是让分散在本地、私有云、Dell AI Factory、非 Dell 基础设施和公有云的数据能够在原地处理，并形成 Agent 可访问、可治理的上下文。
- **核心组件：**
  - **Agentic Data Gateway：** 为 Agent 提供统一、受治理的数据与上下文入口；
  - **Hybrid pipeline orchestration：** 数据管道尽量在数据所在位置执行，减少大规模非结构化数据搬迁；
  - **Storage Intelligence / Data Intelligence：** 暴露异构、十亿级文件环境中的数据来源、质量和使用情况；
  - **Open unified data access：** 将表格、图片、视频和文档纳入统一处理路径，并将向量路由到客户已有数据库，强调不要求先迁移数据库；
  - 与 LangChain、OpenAI Codex、Unstructured.io 等工具集成。
- **性能证据与边界：** Dell 宣称 Agentic Data Gateway 在其内部测试中将 token 消耗最多降低 76%，回答准确率从 60% 提升到 94%。测试使用合成 toll-plaza 数据集、20 个问题、6 类工作负载，以及 NVIDIA Nemotron-3-Super-120B 经 NVIDIA NIM 运行；这是 Dell 2026 年 9 月内部测试，不是第三方独立评测。其“最高 12 倍索引速度”引用的是 Elastic 2025 年公开 benchmark，测试条件为单台 AWS g6.4xlarge、260 万条 1,536 维向量，不能直接视为 Dell 新产品的独立实测。
- **成熟度：** Dell 声明 AI Data Platform 新能力从 **2026 年 12 月**开始提供；因此截至本简报日期仍属于已宣布、待交付能力。新的 Exascale 存储平台预计 2027 年上半年提供。
- **商业验证：** Dell 称 AI Factory with NVIDIA 已有 420 多项产品/服务组合、6,500 多家客户；客户数字基于 Dell 2026 年 8 月订单数据，属于厂商披露的整体 AI Factory 口径，并非 Agentic Data Gateway 的付费客户数。另据 Dell 11 月 20 日公告，Firebird 选择 Dell 支持其在亚美尼亚的下一阶段 AI 基础设施扩张；此前 Hrazdan 第一阶段集群使用 Dell PowerRack、PowerEdge 和 NVIDIA Blackwell，但公告没有披露容量、收入或新数据平台采用情况。
- **竞品 / 相关工作：** 该方案不是新的向量数据库，也不是单纯的 RAG pipeline；它试图占据企业数据访问、上下文治理、数据血缘和底层存储之间的控制层。竞争边界将与云数据平台、数据集成/治理产品和企业存储厂商重叠。
- **独立判断：** 企业 Agent 的瓶颈正在从“模型能否调用工具”转向“能否在正确权限下访问正确数据，并保留来源、质量和生命周期信息”。Dell 的优势是既有企业存储和混合部署渠道；风险是 Agentic Data Gateway 的实际连接器覆盖、授权透传、策略执行、数据血缘完整性和实际可用性尚需产品交付验证。

### 4. Ai2 将 Theorizer 接入 Asta：从文献问答走向可追溯的科学理论与假设生成

- **发布日期：** 2026-11-19（Theorizer in Asta）；底层论文正式发表于 ACL 2026 年 7 月
- **重要性：** A
- **领域 / 类型：** AI Agent、Vertical AI、AI for Science、学术研究与开源
- **对象与目标用户：** Allen Institute for AI（Ai2）的 Asta 是面向科学研究的 Agent 平台。Theorizer 试图把多篇论文中的实验结果组织成可检验的理论、规律和假设，而不只是生成文献综述或摘要。
- **团队与研究背景：** 论文作者 Peter Jansen、Peter Clark、Doug Downey、Daniel S. Weld，机构包括 Ai2、University of Arizona 和 University of Washington。论文《Generating Literature-Driven Scientific Theories at Scale》已收入 ACL 2026 长文论文集，属于正式会议论文，不是仅有 arXiv 预印本。
- **核心技术链路：**
  1. 根据研究问题通过 AI2 PaperFinder / Semantic Scholar 搜索相关论文；
  2. 下载可获取的全文并进行文本抽取；
  3. 为每个研究问题生成定制化 evidence extraction schema；
  4. 从论文中抽取结构化实验变量、条件、结果和限制；
  5. 汇总证据生成候选理论，再通过 reflection 检查一致性、证据归属和适用范围；
  6. 给出支持证据、潜在反证及可供后续检验的预测。
- **研究规模与实验：** 作者使用 13,744 篇来源论文生成 2,856 个理论，并以 4,554 篇知识截止日期之后发表的论文进行 literature backtesting。论文比较 literature-supported 与仅依赖 parametric LLM memory 的生成方式，并区分 accuracy-focused 与 novelty-focused 目标。作者报告：accuracy-focused 条件下，文献支持方案的预测证据 precision 为 0.90，对照为 0.88；novelty-focused 条件下为 0.61 对 0.34。评测使用 LLM judge，并进行 bootstrap 统计检验；这些是作者实验，不是独立实验室复现。
- **成本与限制：** 论文估算 literature-supported theory generation 约 0.26 美元/理论，parametric-only 约 0.04 美元/理论；每个问题生成约需 15–30 分钟，且当前主要受限于可自动下载的开放获取文献。更重要的是，backtesting 不等于真实实验：accuracy-focused 理论约 51% 能在后续文献中找到至少一篇直接检验其预测的论文，novelty-focused 条件仅约 4%；科学文献还存在正结果偏差。系统不能证明某个新理论正确，也不能替代领域专家实验。
- **产品与开源成熟度：** 11 月 19 日起可在 Asta Web 界面试用，Ai2 同时公开 Theorizer 代码；Asta 插件仓库采用 Apache-2.0。Ai2 表示 Web 界面在一定额度内承担 token 成本，本地运行者需自行承担模型 token 成本。未披露独立商业定价、收入或大规模付费客户。
- **真实使用线索：** Ai2 分享的 Peru 气候数据案例中，Theorizer 提出的一个湿度机制假设最终被数据分析排除，但它促使研究人员执行此前未考虑的检验，并追查到数据估算方法的问题。Ai2 同时说明，相关气象站独立观测验证仍在进行。这个案例的价值是“提出可证伪的分析路径”，不是“AI 已发现正确理论”。
- **独立判断：** Theorizer 值得关注的不是自动写论文，而是把来源论文、实验条件、支持/反证和理论适用范围组织成可回查的证据图谱。它与通用 Research Agent 的差异在于强调结构化证据抽取和理论级综合；其主要风险仍是检索遗漏、全文可访问性、跨研究实验条件不可比，以及 novelty 判断超出已检索语料。
- **原始资料：** [Ai2：Theorizer comes to Asta](https://allenai.org/blog/theorizer-in-asta)；[ACL Anthology 正式论文](https://aclanthology.org/2026.acl-long.669/)；[论文 PDF](https://aclanthology.org/2026.acl-long.669.pdf)；[Theorizer GitHub](https://github.com/allenai/asta-theorizer)；[Asta plugins GitHub](https://github.com/allenai/asta-plugins)

### 5. SC26：DySpin 将动态稀疏 Attention、6-bit KV Cache 与 GPU 调度联合设计

- **会议与展示日期：** SC26 论文；报告安排于 2026-11-18。论文早于本周即已录用，不能把会议报告日期误写成论文首次公开日期。
- **重要性：** B（研究方向重要；当前可核验证据主要是官方摘要与报告 slides）
- **领域 / 类型：** AI Infrastructure、AI × Storage、KV Cache、GPU Kernel；学术论文 / 会议
- **团队：** Chengyu Sun、Yaqi Xia、Dazhao Cheng（Wuhan University），Ruirui Pan（Central China Normal University），Donglin Yang（NVIDIA），Xiaobo Zhou（University of Macau）。该工作入选 SC26 Best Paper finalist。
- **研究问题：** 长上下文解码时，KV Cache 不仅受 HBM 带宽限制，也受 GPU 容量限制。传统稀疏 Attention 常用固定的 per-head token budget，无法适应不同 attention head 在不同解码步骤上的实际需求；即使只读取部分 KV page，所有历史 KV 仍可能驻留在 GPU 内存中，容量问题并未解决。
- **核心方法：**
  - **Dynamic allocation：** 依据每个 head、每个 step 的重要性分布动态分配 token/page budget；
  - **FastEstimate：** 融合重要性评估、阈值选择和索引生成，减少单独 Top-K / sorting 的开销；
  - **Load-balanced sparse attention：** 将动态产生的不规则工作映射到 GPU CTA，缓解部分 CTA 空闲、部分 CTA 过载；
  - **6-bit KV Cache：** 采用紧凑的 6-bit packing，并以寄存器级并行 unpack/dequantization 降低存储和读取开销；
  - **FusedRoPE：** 将 RoPE、量化、压缩和 KV append 融合，减少 prefill 阶段重复访存。
- **实验条件与作者结果：** 报告 slides 给出的硬件为 H100 PCIe 80GB 和 RTX 3080 10GB；模型包括 Longchat-7B、Llama-3.1-8B、Qwen3-0.6B；工作负载包括 LongBench、PG19，测试上下文长度覆盖 32K–320K。作者报告在 Longchat 场景下，相对 RocketKV 的端到端速度最高约 1.62 倍；6-bit DySpin 可运行 144K Longchat 和 320K Llama 上下文，而对应稀疏基线在这些极端设置下 OOM。另在 RTX 3080 10GB 上展示了 Qwen3-0.6B 的 128K 上下文可运行性，而稀疏基线 OOM。上述均为作者实验结果，不是第三方复现。
- **成熟度与可复现性：** 官方 SC26 proceedings 页面公开论文摘要和演讲 slides；本次未取得可直接核验的完整论文正文，因此不把 slides 当作完整论文。代码仓库公开，采用 Apache-2.0，README 要求 SM80+ GPU 与 CUDA 12.x；GitHub 最近可见提交停留在 2026-07-13。Zenodo artifact v1.0.0-sc26 于 2026-07-13 发布，压缩包约 112.4KB，页面显示下载量较少。代码和 artifact 已公开，但尚无可靠第三方复现证据。
- **竞品 / 相关工作：** 论文比较 Quest、RocketKV 和 FlashInfer 等稀疏 Attention 路线。DySpin 的区别在于同时优化“选择哪些 KV、如何把不规则工作映射到 GPU、如何压缩驻留 KV 状态”，而不是只调整稀疏策略或单独压缩 KV。
- **独立判断：** 该方向的价值在于把长上下文推理从单纯减少 FLOPs 转向减少 KV bytes、优化动态访存和提高 GPU 利用率。下一步关键不是再看单 kernel speedup，而是验证其与 vLLM / SGLang 等真实 serving runtime 的兼容性、并发请求下的调度开销、不同模型架构的精度损失，以及端到端吞吐和成本。
- **证据限制：** SC26 官方页面目前可核验的是摘要和报告材料；完整论文、完整评测脚本运行结果和独立复现情况仍需进一步检查。
- **原始资料：** [SC26 proceedings 摘要](https://sc26.supercomputing.org/proceedings/papers/paper_pages/pap189.html)；[SC26 报告 slides](https://sc26.supercomputing.org/proceedings/papers/paper_files/pap189s4-file2.pdf)；[SC26 报告日程](https://test.sc26.conference-program.com/presenter/?uid=162024)；[GitHub](https://github.com/sunchengyu1111/DySpin)；[Zenodo artifact](https://zenodo.org/records/21334482)

## 2. 今日产业与学术判断

1. **Agent 产品的核心分化是执行边界，而不只是模型能力。** Dots 将持续任务放在云端计算环境和连接器中；Claude Computer Use 直接触达用户桌面。两种形态的权限、隔离、审计和恢复要求不同。Computer Use 没有 sandbox 的事实尤其说明：端侧 Agent 的产品竞争力必须与权限边界和安全控制一起评估。
2. **生产级 Agent 正从 Prompt / Tool 调用转向 Durable Workflow。** Performance Factory 的任务状态、状态转换、事件订阅、服务身份、反证审查和部署后验证，说明长周期 Agent 更像带有人工决策门的分布式工作流系统。Evaluation 也必须评估因果诊断准确率、恢复率、回滚与副作用，而不只是单轮任务完成率。
3. **企业 AI Data Platform 正在成为 Agent 的上下文控制面。** Dell 的方向不是另造一个数据库，而是把数据位置、治理、来源、质量、向量路由和存储生命周期连起来。真正的竞争力将取决于授权能否透传、来源能否追溯、异构数据能否原地处理，以及 Agent 是否能在既有数据库上工作。
4. **长上下文推理的优化目标从算力转向数据移动与状态容量。** DySpin 把动态稀疏选择、GPU 负载均衡和 6-bit KV Cache 放在同一设计中，反映 KV Cache 已成为影响推理成本和可用上下文长度的系统级状态层，而不是简单的缓存实现细节。

## 3. Agent 专项观察

- **Agent 产品 / 应用：** Dots 向选定 Plus 与 Business Standard 用户 rollout；Claude Computer Use 向 Team / Enterprise 开放 beta。前者是云端持续 Agent，后者是直接操作桌面应用。
- **Runtime / Harness / 长周期任务：** Performance Factory 展示了 task service、dispatch loop、云端 Codex 执行、事件唤醒与人工审批的生产架构。
- **Skill / Tool / 开发者生态：** Asta plugins 以 Apache-2.0 公开，包含 literature review、local library、data analysis、theory generation 和 long-range research assistant 等研究技能。未发现本窗口内足以入选的 MCP / A2A 新协议或主流框架重大版本变化。
- **Memory / Context：** Dots 将 ChatGPT Memory 与自身云端计算环境、连接应用结合；本窗口未发现足以入选的独立 Agent Memory Database 新发布或关键算法突破。
- **安全 / 治理：** Claude Computer Use 没有 sandbox，组织可用 app allowlist / blocklist、角色权限和 MDM 控制，但截图保存与跨文件夹访问风险仍需纳入评估。OpenAI Performance Factory 则展示了 service identity 和人工部署门。
- **Evaluation / Observability：** Performance Factory 披露 100 条根因建议的人工抽查结果（70% 准确，30% 仍需完善或未充分证明因果）；该口径比单纯成功率更接近生产质量，但样本规模仍小且来自厂商内部。
- **商业化：** Dots 披露 Enterprise 分层价格与计费日期；Claude Computer Use 仍处 beta，未披露单独定价。
- **专项结论：** 本日 Agent 主线有达到入选标准的可靠新增，重点是产品执行边界和生产工作流；Memory DB、MCP/A2A、独立 Agent Evaluation Benchmark 与跨 Agent Context 标准本窗口没有足够可靠新增，不为凑数补项。

## 6. 观察盲区与证据限制

1. **近24小时产业新增偏少。** 未找到足以通过来源和证据门槛的数据库内核、云数据库、分析平台、GPU Cloud、RDMA/CXL 或中国 AI 创业公司重大新发布。今日五项主要是近7日内的产品、内部实践和学术会议进展。
2. **厂商指标不能等同于独立验证。** Dell 的 token 与准确率数据来自内部合成工作负载；OpenAI 的调查量和准确率来自自身生产环境及人工抽样；两者都需要外部客户或独立评测补证。
3. **Computer Use 的安全风险仍高。** Anthropic 官方文档明确无 sandbox，且截图、应用间跳转、文件访问范围等风险不能只靠“允许应用列表”消除。
4. **Theorizer 的 backtesting 不等于真实科学发现。** 论文已正式发表于 ACL 2026，但其核心评价依赖后续文献是否检验预测；真实实验、长期理论演化和跨学科非开放文献仍未充分覆盖。
5. **DySpin 的复现证据不足。** 当前可核验的是 SC26 官方摘要、演讲 slides、公开代码与 Zenodo artifact；未取得完整论文正文，也未发现可靠第三方复现。仓库最近可见提交停留在 2026-07-13，需进一步观察维护活跃度。
6. **中国市场扫描仍需持续补强。** 本期学术项目中有武汉大学、中央民族大学、澳门大学和 NVIDIA 的合作团队，但没有找到同等证据强度的中国新创业公司融资或产品商业化公告；不能据此推断国内市场没有进展。

**本期结论：** Agent 产业化的重点正在从“能否调用工具”转向“能否持续执行、保留状态、受控访问数据并证明结果”；企业数据平台则开始围绕 Agent Context 和治理形成新的控制层；推理基础设施继续向 KV Cache 的动态选择、压缩和 GPU 数据路径协同优化演进。
