## 1. 今日最值得关注的 5 组进展

### 1.1 LangChain 把 LangSmith 推向 Agent Runtime + Improvement + Governance 控制平面，Tool Gateway 进入 Public Beta

- **发布日期：** LangSmith Tool Gateway：2026-11-19；LangSmith 新能力发布活动：2026-11-20；融资公告：2026-11-13。
- **重要性：** A
- **领域/类型：** AI Agent、Agent Runtime、Tool/MCP、Observability/Evaluation、Agent Security；产品发布/融资。
- **解决的问题：** 企业 Agent 从单轮问答转向常驻、定时、事件触发和长周期执行后，工程团队必须同时管理 Agent 的运行状态、上下文、工具权限、用户身份、模型成本、执行轨迹和持续改进。把 OAuth、API Key、工具白名单和日志分别写进每个 Agent，会快速形成难以维护的权限碎片。
- **团队与背景：** LangChain 由 Harrison Chase 等人创立。公司于11月13日宣布完成 **3亿美元 Series C、3 billion 美元估值**，由 CapitalG 领投，GIC、DFJ Growth、IVP、Sapphire Ventures 等参与。融资和估值为公司公告口径。公司称 LangSmith 已有超过7,000家组织使用，Clay 每月监控数亿次 Agent Run，Workday 将新 Agent 部署周期从5个月缩短至不到1天；均为公司提供的客户案例数据，未见第三方审计。
- **核心技术与架构：**
  1. **Agent Runtime：** Deep Agents 作为可修改的开源 Harness；LangSmith Agent Server 提供 Durable Execution、Thread/State、Checkpoint、Task Queue、Cron、Streaming Reconnect、Sandbox 和 Context Hub；Managed Agents/Fleet 将 Harness 与托管运行环境打包。
  2. **Agent Improvement：** Trace、Evaluation、线上监控与回归测试形成反馈环。LangSmith Engine 是运行在 Trace 之上的 Agent，识别失败、生成 Eval 和代码/Prompt 修复建议，再由工程师审核合并。11月20日活动还展示 Coding Agent 视图，将 Trace/费用与 GitHub PR 等结果关联。
  3. **Agent Governance：** LLM Gateway 管模型调用、预算、Fallback、Rate Limit 和敏感信息处理；新推出的 Tool Gateway 管工具访问、身份和审批。
  4. **Tool Gateway（Public Beta）：** 将 MCP Server 注册一次，通过单一 URL/Tool Kit 提供给多个 Agent；支持按 Agent/User 限制可见工具、Search Mode 按需加载工具；身份可选择“代表用户执行”或“代表 Agent 执行”；可设置 Deny Policy 与 Human Approval Policy；工具调用进入 LangSmith Trace，记录 Server、User、Credential Identity、Outcome 和 Latency。官方说明工具输入/输出正文默认不写入 Trace，以降低敏感数据暴露。
  5. **Trace 数据权限：** 11月20日发布活动介绍按 User Group 和 Trace Metadata 控制谁能查看输入/输出、谁能访问特定 Trace；Coding Agent 专用视图则尝试把 Token/Cost 与 PR 等工程结果关联。
- **成熟度与商业模式：** Tool Gateway 明确为 **Public Beta**，不是 GA。LangSmith 平台已商业化；本轮未发现 Tool Gateway 独立定价。官方文章表示 Enterprise Audit Log、部分 Deny Policy 能力需联系团队获取，不能默认所有计划均包含。
- **竞品/相关方案：** AWS Bedrock AgentCore、Microsoft Agent 365/Foundry、Google Agent Platform、Salesforce Agentforce，以及企业自建 MCP Gateway + OAuth/OIDC + OPA/Policy Engine。LangChain 的差异在于把 Harness、Runtime、Trace/Eval、Model Gateway 和 Tool Gateway 放入同一 Agent Engineering 产品，而不只是提供 Workflow Builder。
- **独立判断：** 这是本周 Agent 平台最值得关注的产品变化之一。企业真正需要的不是更多 MCP Server，而是一个可按用户、Agent、工具和执行上下文做确定性授权的控制点。Tool Gateway 的单一入口、身份映射、审批和 Trace 是正确方向；但“工具已授权”不等于“参数和业务动作正确”，仍需对金额、数据范围、写入对象、幂等键、事务边界和高风险操作做语义/数据层校验。另一个权衡是 Trace 不保留工具输入输出，有利于隐私，却可能降低事后取证能力；企业需有受控的证据留存机制。Public Beta 阶段应重点验证策略覆盖率、撤权延迟、凭证轮换、跨租户隔离和失败恢复。

### 1.2 Remanence 获得 3,000 万美元 Seed：把 Agent 生产 Trace 转成训练环境，再用 RL 训练企业自有模型

- **发布日期：** 2026-11-17。
- **重要性：** A
- **领域/类型：** AI Agent、Agent Evaluation、AI for Software Engineering、AI Infrastructure；创业公司/融资/产品方向。
- **解决的问题：** 企业 Agent 在生产中每天产生大量 Tool Call、失败、人工修正和成功轨迹，但大多只用于日志和 Debug。若这些经验不能转化为可重复训练任务，下一次运行仍使用通用模型，重复同类错误并持续支付 API 成本。
- **团队与背景：** 创始团队 Pierre-Louis Cedoz（CEO）、Hamza Benchekroun（CTO）、Axel Moyal（CPO）此前在 H Company 负责 Holo 开放权重模型的 Post-training，并有 Google DeepMind、InstaDeep 等经历。FirstMark 与 EQT Ventures 联合领投3,000万美元 Seed，其他投资方包括 Zero Prime、Emblem、Drysdale、Global Founders Capital、Yellow 等。融资与团队背景由两家投资机构公告确认。
- **核心技术与架构：**
  1. **Trace Analysis：** 接入企业现有 Agent Observability，定位失败模式和高价值任务。
  2. **Environment Synthesis：** 从 Trace 自动生成可交互的任务环境、Sandbox 和 Verifier；目标是模拟企业真实系统，而不是仅把对话记录转成 SFT 样本。
  3. **Long-horizon RL：** 在生成的环境中对 Open-weight Model 做长周期强化学习，以客户当前生产模型作为 Baseline。
  4. **Inference：** 提供托管推理或客户自有 Cloud/VPC/On-prem 部署。公司和投资方称客户拥有训练后的模型权重，客户 Trace 只用于自己的模型，数据可留在客户基础设施内。
  5. 新融资将用于建设欧洲专用 GPU Cluster，并扩充 Paris、London、San Francisco 的研究与工程团队。
- **成熟度与商业验证：** 官网目前以 Book a Demo 为主。FirstMark 称公司已与欧洲和美国的 Legal、Customer Support、Enterprise Software 客户开展 Design Partnership，但未披露客户名称、付费合同、生产规模、成功率或成本节省。尚无公开 GA 版本、定价或可下载产品。
- **竞品/相关工作：** LangSmith Engine、LangSmith Fine-Tuning、Prime Intellect、Adaptive/Predibase 等 Post-training/RL Infra，以及企业内部基于 OpenTelemetry Trace + 自建 Sandbox + GRPO/RL Pipeline 的方案。Remanence 的定位更偏向“Trace → 环境合成 → Verifier → Long-horizon RL → 自有模型”的端到端闭环。
- **独立判断：** 这是值得建立长期档案的新创业方向。Agent 的护城河可能从 Prompt/Harness 迁移到企业私有的任务环境、状态转移、失败轨迹和 Verifier；这类数据既能改进模型，也能形成企业专有 Evaluation。最大技术风险是 Environment Gap：合成环境是否保留真实业务系统的权限、时序、并发、外部副作用和异常分布；其次是 Verifier 是否能可靠评价多步骤任务，避免 Reward Hacking。商业风险是 RL Compute 与环境维护成本可能吞噬节省的推理成本。当前融资和团队可信度较高，但商业化仍处于 Design Partner 阶段，不能把投资方叙述当作已验证 ROI。

### 1.3 ROGUE-AI：把真实 Agent 事故重建成“事故条件 + 匹配对照组”，发现大量风险并非 Prompt Injection

- **首次公开：** 2026-11-19 18:23:35 UTC（北京时间11月20日02:23）。
- **重要性：** A
- **领域/类型：** Agent Security、Evaluation、Multi-Agent、可靠执行；学术预印本。
- **论文状态：** arXiv:2611.26553 v1，尚未发现正式录用/同行评审信息。作者实验结果不等于第三方复现或生产环境风险率。
- **作者/团队：** Mengxiao Wang（Jackson Wang）、Mahbub Alam、Kalyan Nakka、Nitesh Saxena，均可在 Texas A&M University 的 SPIES Lab 官方人员/团队页面核实。SPIES Lab 由 Nitesh Saxena 教授领导，研究 AI Security/Privacy 与 Autonomous Agents。
- **研究问题：** Agent 事故报道通常只描述结果，不一定验证事故是否可复现，也很少证明报道所指的根因。传统 Incident Catalog 负责收集和分类；Prompt-Injection Benchmark 主要测攻击输入；两者都不能回答“如果只移除被指认的危险因素，Agent 是否就不再造成损害”。
- **方法与架构：**
  1. 从253份公开事故报告中建立 Incident Catalog，核对 Primary Source；作者称修正了76条记录，并发现2条与原始来源矛盾。
  2. 由多 Agent Pipeline 完成事故分类、Claim Card、环境构建和复核；Builder、Path Reviewer、Domain Reviewer 分工，Reviewer 与 Builder 使用不同模型供应商。
  3. 每个场景构建 Incident Condition 与 Matched Control，二者只在报告指认的 Hazard 上不同。
  4. 用真实状态差异（如文件/数据库行/权限状态）判断是否发生 Harm，而不是相信 Agent 自己的最终解释。
  5. 对结果使用 Fisher’s Exact Test，并对多重检验做 Benjamini–Hochberg 校正；对未复现案例再做 Diagnose-Fix-Rerun。
  6. 论文共尝试108个 Replication，主实验运行五个模型（GPT-5.6-luna、GPT-5.6-sol、Claude Sonnet 4.6、Gemini 3.5 Flash、DeepSeek-V4-Flash），主运行共6,439个完成 Session。
- **主要实验结果（作者自报）：**
  - 五个模型在 Incident Condition 中的 Harm Rate 为18%—33%，Matched Control 为0%—1%。
  - 72个造成现实伤害的 Incident 中，62个没有底层攻击者；典型问题是 Agent 按任务执行，却忽略共享生产数据库、危险文件路径或权限过宽等普通环境风险。
  - 论文所称“89%复现率”包含后续修复循环：主实验中32个 Replication 被判为 Supported、23个 Suggestive、51个未复现、2个无 Control；随后 Diagnose-Fix-Rerun 又复现其中39个，因此得到39/51的补充复现，合并后报告89%。不能把89%误读为当前模型在真实生产环境中的事故概率。
  - 无攻击者的场景对五个模型造成的伤害多于不可信指令/Prompt Injection 场景。作者报告的12个已发布产品 Prompt-Injection Replication，在五个模型上共180个 Session 仅2次造成 Harm。
  - 在 Tool Output 中直接提示“危险是什么 + 会造成什么后果”，比只给同长度中性说明更有效；提示应贴近执行动作，而不是只把规则写在 System Prompt。
- **实验限制与可复现性：** 所有模拟数据均为 Synthetic；没有触碰真实账户、钱包或生产服务。只有10个破坏性动作场景在 Codex CLI/Claude Code 产品中做了有限复测，且关闭了审批提示，不能代表默认产品设置。事故报告本身缺少原始上下文，部分场景必须做中性补全；模型标识和 API 快照仍需进一步核验。论文称已公开代码、Replications 和 Session Logs，Artifact 页面可访问，但本轮未确认完整仓库地址与 License，也未找到独立第三方复现。
- **与已有工作的差异：** 相比 AgentDojo/Agent-SafetyBench 的设计型攻击 Benchmark、Incident Registry 的事故分类、Chronicle 的 Trace Replay，ROGUE-AI 的关键增量是从真实事故出发，建立只差一个 Hazard 的匹配对照，并用代码判断最终状态。
- **独立判断：** 这篇论文对企业 Agent 安全设计有直接影响：只加强 Prompt Injection 防护并不够。生产事故常来自用户任务本身、共享环境、工具权限过宽、错误目标和缺少临近动作的危险提示。企业应把 Least Privilege、隔离测试/生产数据、Scoped Credential、动作前检查、可撤销权限和事务边界作为基础控制。论文值得复现，但89%是经过修复循环后的框架结果，不能直接转成产品事故率。

### 1.4 GrepMem：不用 Embedding/Vector DB，把完整历史留在 Append-only Log 中按需 grep

- **首次公开：** 2026-11-18 20:02:57 UTC（北京时间11月19日04:02）。
- **重要性：** A
- **领域/类型：** Agent Memory、Context Engineering、Long-horizon Agent；学术预印本 + 开源实现。
- **论文状态：** arXiv:2611.25123 v1，尚未发现同行评审录用信息。
- **作者/团队：** Ziyan Yang、Taiwei Shi、Jieyu Zhao；University of Southern California。GitHub 仓库由作者团队公开。
- **研究问题：** 长周期 Agent 的历史会超过 Context Window。Summarization、Masking 和 Structured Memory 都必须提前决定保留什么，可能把之后任务需要的细节压缩掉。
- **核心方法：**
  1. 使用 Append-only Plain-text Log 保存完整对话与 Tool Output，不在记忆写入时删除原始历史。
  2. Agent 先压缩当前 Working Context，需要时调用 Regex Search 工具 grep_history，从原始历史中按需恢复细节。
  3. 使用 RL 训练 Qwen3.5-9B，使同一 Policy 学会研究、总结和按需回忆；不需要额外 Embedding Model、Vector Index 或 Memory Extraction Model。
  4. 研究任务仍可使用独立 Document Retrieval Server；论文所说的 Index-free 指 Agent 自身历史记忆，不是把所有外部知识检索都替换成 grep。
- **实验与结果（作者自报）：** 比较 ReAct、SUPO Summary、Observation Masking、MemGPT 和 GrepMem。测试包含 BCP-Multi、AMA-Bench File/Stream、ContextBench KV/Log。GrepMem 在 ContextBench KV/Log 分别达到97.4%/95.3%；Masking 为20.7%/6.6%，SUPO 为13.9%/6.6%，MemGPT 为99.9%/50.0%。在 BCP-Multi 上 GrepMem 为46.9%，SUPO 为38.1%。AMA-Bench 上各策略差异较小，作者也明确指出部分差异不确定。
- **Artifact/许可证/活跃度：** [limenlp/GrepMem](https://github.com/limenlp/GrepMem) 已公开 MIT License、代码、Tests 和 Reproduction Guide；仓库页面显示1次 Commit、3 Stars、1 Fork，属于刚公开的早期仓库，不能用 Stars 判断成熟度。README 明确说明训练后的 RL Checkpoint 尚未公开，Quick Start 使用的是 Base Model，不是论文完整训练结果；完整复现实验需要 GPU、数据下载、Judge、Document Retrieval 和 RL Training 环境。
- **竞品/相关工作：** MemGPT/Letta、Mem0、Zep/Graphiti、传统 RAG/Vector Memory。GrepMem 的优势是简单、低依赖、保留原始证据；弱点是 Regex/关键词搜索不天然理解语义改写、实体关系和跨语言同义表达，历史日志仍需做访问控制、保留期限和隐私清理。
- **独立判断：** 这是一个值得做 Baseline 的研究，而不是“Vector Memory 已被淘汰”。它提醒 Agent Memory 研究者把“写入时不丢信息”和“未来能准确检索信息”分开测量。对长周期 Agent，Append-only Log + Summary + Search 可能是成本低、可审计的第一层；复杂语义记忆仍需要结构化、向量或知识图谱能力补足。
- **原始资料：**
  - [arXiv:2611.25123 — Forget Freely, Grep Later](https://arxiv.org/abs/2611.25123)
  - [GrepMem GitHub（MIT）](https://github.com/limenlp/GrepMem)

### 1.5 数据平台本周同时推进“数据正确性修复”和“Agent 可委托身份”：DuckDB 2.0.1 LTS + Snowflake Postgres Token Access Roles GA

- **发布日期：** DuckDB 2.0.1：2026-11-20；Snowflake Postgres Access Roles：2026-11-20 GA；Snowflake Cortex Agent SDK 1.0：2026-11-18 GA。
- **重要性：** A
- **领域/类型：** Database × Storage、AI × Database、Agent Security；正式版本/GA。
- **DuckDB 2.0.1 LTS：**
  1. 这是2.0 LTS 的首个 Patch；DuckDB 1.4 LTS 社区支持已于11月17日结束，2.0 LTS 支持至少到2027年10月。
  2. 修复 Linux 部分 Kernel 上可能因 MADV_FREE 行为导致的静默内存归零/数据丢失风险；通过调整内置 jemalloc 的 muzzy_decay_ms 避免该路径。
  3. 修复 enable_external_access=false 时仍可 CREATE SECRET、远程路径穿越，以及 Brotli Decoder 安全问题。
  4. 修复 DuckDB 2.0.0 读取1.x 文件时 NULL 行可能被过滤掉的问题；修复 Bulk Insert 在 Commit 前对其他事务可见、WAL Replay 后索引项丢失、Reverted Commit 后重启丢行等 Storage/Transaction 问题。
  5. SECRET Scope Matching 改为精确 Host/Bucket 边界匹配，避免同前缀不同 Bucket/Host 被错误匹配；自定义 Extension Repository 可通过域名和 .well-known 元数据发现并 Pin Signing Key。
  6. UPDATE FROM/MERGE 恢复1.x“每个匹配行都更新一次”的语义；当一个 Target 匹配多个 Source 时，最终值可能非确定。应用升级前应检查 SQL 语义依赖。
  7. pg_duckdb 发布覆盖支持 PostgreSQL 版本的二进制，并改善 Citus/pgvector 兼容性；Postgres Extension 对单一附加 PostgreSQL 数据库的查询可下推到 PostgreSQL 执行。
- **Snowflake Postgres Token Access Roles GA：**
  1. 为 Snowflake Postgres 用户启用 Access Role，并把它授予 Snowflake Role、Application Role 或 User；授权调用方可生成短期 Token，以指定 Postgres 用户身份连接。
  2. Token 有效期15分钟；Postgres 数据库与对象权限仍由 Postgres Role 控制，Snowflake Role 只负责委托登录资格，不取代数据库内授权。
  3. 撤销 Snowflake Grant 会阻止新 Token 的生成，但不会使已签发 Token 立即失效，也不会关闭已经建立的连接；若要阻断旧 Token 的新连接，需要禁用该 Postgres 用户的 Access Role 或删除用户，已建立 Session 仍需单独管理。
- **Snowflake Cortex Agent SDK GA：** Python/TypeScript SDK 1.0.0 正式 GA，支持运行 Cortex Agent/Cortex Code、Streaming、Conversation/Thread 维护，以及重新连接长时间运行的任务。
- **成熟度与验证：** DuckDB 2.0.1 是正式 Patch/LTS；Snowflake Postgres Access Roles 和 Cortex Agent SDK 均为 GA。以上是官方 Release Notes/文档声明，未涉及性能 Benchmark。
- **独立判断：** DuckDB 2.0.1 的价值不在新功能数量，而在于一次性修复多项数据正确性、事务可见性、WAL/索引持久化和安全边界问题，属于生产升级必须认真评估的 Patch。Snowflake 的 Token Access Roles 则展示了 Agent 访问数据库的一种较合理路径：把短期登录凭证与数据库对象权限分离。企业仍需验证 Token 生命周期、Connection Pool、撤权、现有 Session 清理、审计和最小权限，不能把“短期 Token”误认为自动实现了细粒度 SQL 授权。

## 2. 今日产业与学术判断

1. **Agent 平台正在从 Framework/Workflow 转向企业控制平面。** LangSmith 将 Runtime、Improvement、Governance 合并；Snowflake 用 Postgres Access Role 把数据库身份委托给应用/Agent；InstaLILY 把 Specialist Agent 放进 Dynamics 365 的销售机会 Room。下一阶段差异化不只是 Agent 能否调用工具，而是能否对“谁在什么上下文、以什么身份、对哪个对象执行什么动作”做确定性控制。
2. **Agent 经验开始成为可训练资产。** LangSmith Engine 从 Trace 生成 Eval 和修复建议；Remanence 更进一步，从 Trace 合成环境与 Verifier，再做长周期 RL。两者不是简单的 Memory DB：前者偏工程改进闭环，后者偏企业专用模型训练。关键壁垒将是环境保真度、任务验证器和可复现的业务收益。
3. **Agent 安全不能只围绕 Prompt Injection。** ROGUE-AI 的预印本结果提示，任务本身、环境危险、过宽权限和不完整上下文可能比恶意指令更常见。企业应优先建设 Least Privilege、独立测试/生产数据、Tool Gateway、短期凭证、动作前检查和可撤销执行。
4. **数据正确性与身份边界仍是 Agent 的地基。** DuckDB 2.0.1 修复事务/索引/存储问题，Snowflake Postgres Token Role 细化登录委托，DiskANN 研究继续推进 ANN 搜索成本/召回权衡。Agent 推理再强，也无法弥补错误数据、错误授权和错误事务边界。

### 4.1 Variants of Beam Search for DiskANN

- **首次公开：** 2026-11-19 18:57:05 UTC（北京时间11月20日02:57）。
- **论文状态：** arXiv:2611.26609 v1，预印本；本轮未找到公开代码仓库或第三方复现。
- **作者/机构：** Viraj Agrawal、Kirankumar Shiragur，论文首页标注 Microsoft Research India。
- **问题与方法：** 研究 DiskANN/HNSW/NSG 图索引的 Beam Search 计算预算分配。论文提出 Beam Predictor：先做短 Pilot Search，提取访问节点及距离特征，再预测每个 Query 的 List Size；训练目标是在给定平均 Recall 下，最小化整个 Batch 的 Distance Computation。
- **实验设置与结果（作者自报）：** 数据集来自 NeurIPS’21 Billion-Scale ANN Challenge：SIFT100M（128维 uint8、10,000 queries）、DEEP100M（96维 float32、10,000 queries）、MSSpaceV100M（100维 int8、去重后28,690 queries）。每个 Query Set 用 seed 42 做一次50/50切分，前半训练 Beam Predictor，后半报告主结果；第6.4节另做10次随机切分分析。硬件为2× Intel Xeon Platinum 8160（总计48核/96线程）、512 GB RAM、3.2 TB Dell PM1725a NVMe SSD。索引使用 Vamana Fast Preprocessing，R=32、L_build=100、α=1.2；SSD 指标是 Mean Query Latency 与 Mean SSD Reads，内存指标是 Mean Distance Computations。匹配 Recall 时，Beam Predictor 相对 Classical Beam Search（CBS）在15个 SSD 设置中的14个更快，最高降低29.6%，另一个设置慢0.6%且在 Run-to-run Variation 内；相对 Adaptive Beam Search（ABS）在15个设置中的11个更快，最高6.5%，其余最多慢1.4%。在内存场景中，Distance Computation 相对 CBS 减少1.3%—23.7%，相对 ABS 减少0%—3.9%。论文报告的是 Mean 指标，没有给出足以支持生产 SLO 的 P95/P99 结论。
- **关键限制：** 论文理论保证依赖 α-reachable / sorted α-reachable Graph；其严格定义对应 DiskANN Slow Preprocessing，朴素构建成本为 O(n³)。实验采用实际常用的 Fast Vamana Preprocessing Graph，而作者明确承认这些实际图不已知满足理论条件，因此理论保证不覆盖实验图，也不能直接套到生产构建的 DiskANN 图上。主结果虽有训练/测试切分，但第6.4节多组 Ablation 为了匹配 Test Recall 会在 Test Half 调整 Scale Factor，阅读对比时需区分主评估与 Ablation。延迟数字均为作者单机实验，缺少第三方复现与 P95/P99 报告。arXiv 页面标注 CC BY-SA 4.0；本轮未发现公开代码仓库。
- **价值判断：** 这是向量检索系统中“按 Query 难度动态分配 Beam Budget”的有价值方向，尤其适合 SSD-resident ANN；值得在真实向量库上复现 P95/P99、Recall、SSD I/O 和 CPU Distance Computation，而不仅比较 Mean Latency。
- **原始资料：** [arXiv:2611.26609（摘要/作者/提交时间）](https://arxiv.org/abs/2611.26609) · [arXiv HTML 全文（实验设置、硬件、理论限制、License）](https://arxiv.org/html/2611.26609v1)
