1.2 Xata 带来的关键技术：Branch per Agent Run
Xata 的核心技术是基于 Copy-on-Write 的 PostgreSQL 数据分支。

传统情况下，如果每个 Coding Agent 都需要一份生产数据库副本，会遇到：
- 数据复制时间长；
- 存储成本高；
- 大规模并发创建困难；
- 测试环境与生产数据难以保持一致。
Xata 的方案：
                  Production PostgreSQL
                          |
             Copy-on-Write Snapshot
                          |
          +---------------+---------------+
          |               |               |
          v               v               v
       Branch A         Branch B         Branch C
       Agent #1         Agent #2         Agent #3
          |               |               |
       Own Compute     Own Compute     Own Compute
          |               |               |
       Test SQL        Run Migration    Tune Index
          |               |               |
       Destroy         Destroy          Hibernate

Xata 官方披露的能力：
- 多 TB 数据库创建分支约 3 秒；
- 每个分支拥有独立计算节点；
- Copy-on-Write，避免完整复制底层数据；
- 空闲计算资源自动暂停；
- 恢复连接约 1 秒；
- 支持生产数据脱敏后创建开发分支。
这些数字是 Xata 的产品披露，并非独立第三方基准。Xata

2.4 独立判断
Bay 值得关注，因为它切中了企业 Agent 生产化中的一个关键问题：

Agent 的风险不只是模型生成了错误内容，而是它可能使用正常权限执行了不应该执行的操作。

不过，Bay 也面临几个技术问题：
1. 如何确保所有 Agent Tool Call 都经过 Enforcer？
2. Agent 使用脚本、Shell、Browser 或自定义 API 时，是否能够覆盖？
3. 策略由过去 30 天行为学习，是否可能把历史错误权限当作正常行为？
4. 误报率低于 1% 的同时，漏报率是多少？
5. 是否能够处理多步事务、部分执行、超时和 UNKNOWN 状态？
我认为 Agent Security 会逐渐分化为三层：
层次	解决的问题
Prompt / Model Security	模型是否受到恶意输入影响
Agent Runtime Security	Agent 能调用哪些工具、执行哪些动作
Data / Transaction Security	操作是否破坏数据正确性，能否验证和恢复


Bay 主要覆盖第二层。它不会替代数据库原生权限、事务约束、验证和恢复机制。

关键实现：

第一，数据库原生 Row-level Security。

每个 Agent 使用独立数据库身份。数据库通过 RLS 对每条 SQL 自动附加数据访问限制。

即使 Agent 自己生成了一个查询所有患者数据的 SQL，也只能读取其身份允许访问的数据。

第二，数据库 Trigger 限制 Agent 写操作。

例如，只有 Medication Safety Agent 可以提出药物变更建议。其他 Agent 即使调用相同的 Proposal Tool，也会被数据库 Trigger 拒绝。

第三，模型不能直接决定审批。

Agent 只能提交结构化 Proposal，不能直接修改关键业务记录，也不能自行批准自己的操作。

第四，事实验证。

Agent 生成报告时必须引用数据库记录 ID。程序会逐一回查每个 ID，检查其是否真实存在、是否属于当前用户可访问的数据。

第五，Sandbox。

Agent 运行在独立的 NVIDIA OpenShell Sandbox 中，只能访问明确允许的数据库和模型服务地址，不能任意访问公网。Oracle Blogs

- Agent 生成的法律结论是否能被追溯和审计。
这是一个值得跟踪的垂直 Agent 案例，但目前新产品仍处于 Closed Beta，不能把它当成已经完成规模化验证的自主法律 Agent。
二、今日产业与学术判断
趋势一：Agent 的数据库需求正在从“存储记忆”扩展到“提供独立执行环境”
ClickHouse/Xata 的方向和 Oracle 的方向有所不同，但实际上互补。
方向	解决的问题
ClickHouse + Xata	Agent 每次运行需要独立、可销毁的数据库环境
Oracle + Deep Agents	Agent 需要持久化状态、记忆、身份和权限
两者结合后的目标	Agent 有独立工作空间，同时可以安全访问企业系统


未来 Agent Runtime 可能不只是分配 CPU、Memory 和 Sandbox，还需要为每个任务分配：
- Database Branch；
- Context Store；
- File Workspace；
- Credentials；
- Policy Scope；
- Checkpoint；
- Verification State。
这可能成为新一代 Agent Runtime 的重要基础能力。
趋势二：Agent Security 正在从“模型输出是否安全”转向“系统状态是否允许改变”
Bay 的 Action Firewall 和 Oracle 的 Database-enforced Policy 代表了两种不同的实现方式。

前者在 Agent 动作执行之前进行策略拦截；后者将权限和业务规则放在数据库中。

未来企业 Agent 的安全体系应该至少包含：
Prompt / Model Guardrails
          |
          v
Agent Runtime Policy
          |
          v
Tool / API Action Control
          |
          v
Database Authorization
          |
          v
Transaction / Invariant Check
          |
          v
Audit / Recovery

只依靠 Prompt 约束 Agent，不足以保护企业数据库和核心业务系统。
趋势三：AI Storage 的投资逻辑正在从 GPU 配套存储走向长期数据基础设施
VAST 的 200 EB 供应安排和头部客户承诺金额，说明存储采购正在进入更长周期。

同时，Agent 会持续生成和保留：
- 历史 Session；
- 工具执行结果；
- 文件和代码状态；
- 长期 Memory；
- KV Cache；
- Trace 和 Audit。
这些数据具有不同的访问频率、生命周期和恢复要求。

未来 AI Storage 的重要竞争点可能是：

不只是存储多少数据，而是如何让数据在 Agent、GPU、数据库、文件系统和对象存储之间以合适的成本和语义持续存在。
趋势四：垂直 Agent 正在从问答界面走向业务执行入口
Lexroom 把法律 Agent 放入 WhatsApp，Zoom 则开始通过开发者计划向创业公司开放语音、语言和决策 API。

这说明 Agent 应用层的竞争可能不再只围绕 Chat UI，而是围绕：
- 已有业务入口；
- 企业数据访问；
- 领域知识；
- 可执行工作流；
- 人工审批；
- 结果责任。
通用 Agent 平台和垂直 Agent 应用的边界会逐渐变得模糊。

4. Bay 的安全指标： 误报率低于 1% 是公司披露，尚无公开独立评估。需要同时关注漏报率和 Hook 覆盖率。
5. ClickHouse/Xata 的 Agent Tier： 目前仍是产品路线图。数据库 Branch 已有产品能力，但 Agent 专属数据库层尚不能视为全面 GA。
6. VAST 的 100 亿美元： 是软件和配套硬件的客户承诺总额，不是收入，也没有足够信息拆分为软件、硬件和实际交付。

本日最终结论
今天值得长期跟踪的不是某一个 Agent Framework，而是三种正在成形的基础设施能力：
方向	代表项目	核心变化
Agent Database Environment	ClickHouse + Xata	每个 Agent Run 可以有独立数据库分支
Agent Security Control Plane	Bay	从 Prompt 检查走向执行动作检查
Agent State & Governance	Oracle + Deep Agents	数据库开始承担 Agent 身份、权限、记忆和状态


这三条线共同指向一个新的产品边界：

未来的 Agent 平台不应该只负责运行模型和调用工具，还应该能够为 Agent 提供独立数据环境、持久状态、可信授权、执行验证和可审计的操作历史。

而这也意味着 Database、Storage、Runtime 和 Security 不再只是 Agent 周边的基础设施，它们正在成为 Agent 产品本身的一部分。
