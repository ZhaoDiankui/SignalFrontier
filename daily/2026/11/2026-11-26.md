### 1. ClickHouse 与 AWS 扩大五年战略合作：从实时分析数据库走向 Agent-ready Enterprise Data Stack

- **发布日期：** 2026-11-23
- **重要性：** A
- **领域/类型：** Database、AI × Database、Agent、Observability、Security；产业/商业合作
- **核心事实：** ClickHouse 宣布与 AWS 扩大五年 Strategic Collaboration Agreement。公告所称的“超过 15 亿美元”是 ClickHouse 在 AWS 上潜在软件、服务和解决方案支出的框架规模，不是 AWS 向 ClickHouse 投资 15 亿美元，也不能视为已经确认的收入或不可撤销采购额。公告称 ClickHouse Cloud 全球客户超过 5,000 家；自 2024 年 12 月首次合作以来，其 AWS 客户数增长约四倍，均为公司披露口径。

**产品与架构变化**

这次合作不只是云市场上架或联合营销。ClickHouse 正在把分析引擎周边的事务、可观测性、安全和 AI 工程能力组合成一个可供 Agent 使用的数据平台：

1. **数据面：** ClickHouse Cloud 继续承担实时分析和数据仓库；ClickHouse Managed Postgres 提供事务型数据服务。
2. **Agent 数据访问：** ClickHouse 将深化与 Amazon Bedrock、Bedrock AgentCore、Amazon Quick 的集成，支持 AWS 上构建的 Agent 通过 MCP 查询实时 ClickHouse 数据。
3. **Agent 运行可观测性：** Langfuse 提供 AI Gateway、Tracing、Evaluation 和 Monitoring；ClickHouse 将把 Agent observability/evals 作为重点方向。
4. **Agent 状态与安全：** Managed Postgres 被定位为 Agent transactional state/memory 的承载层；ClickHouse Security 则面向安全遥测与 AI-assisted security operations。
5. **云基础设施：** ClickHouse Cloud 在 AWS 上默认使用 Graviton，并计划扩展更多 AWS Region 和部署选项。

**成熟度必须拆开看**

- ClickHouse Managed Postgres：在 AWS 上 GA。
- ClickHouse Observability：Public Beta。
- ClickHouse Security：Private Preview。
- MCP、Bedrock AgentCore、Amazon Quick 的集成属于持续深化的合作范围，不能把整套平台都写成 GA。

**商业验证与竞品**

- ClickHouse 表示合作将提供最高可达此前四倍规模的 AWS go-to-market funding，支持 POC、迁移和集成项目。
- Sony LIV 的平台工程负责人在公告中披露其使用 ClickHouse 做实时分析和 Observability；这是客户引述，不是独立性能评测。
- 对手不只是 Snowflake/Databricks，也包括 PostgreSQL 托管服务、Elastic/Splunk、Datadog 等在事务、日志、Tracing 和 Security 上的专业产品。

**独立判断**

这是 ClickHouse 从“高性能分析数据库”向“企业 Agent 数据平台”扩张的商业信号。它的优势是把实时分析、事务状态、日志/Trace、安全遥测和 AI 工程组件放在一个开放组合栈里，减少数据复制和跨产品切换。但真正的壁垒仍取决于统一权限、数据语义、事务一致性和跨产品运维体验，而不是产品目录变长。尤其需要持续观察 Beta/Private Preview 功能能否形成稳定的生产 SLA。

### 2. Zipher 出隐身并披露 5,300 万美元融资：Agent 开始直接管理数据工作负载执行

- **发布日期：** 2026-11-24
- **重要性：** A
- **领域/类型：** AI Agent、AI Infrastructure、Database/Data Engineering；新公司/商业产品/融资
- **公司背景：** Zipher 由 Dan Coster（CEO）和 Yoav Gill Ben Ephraim（CTO）于 2024 年创立；两位创始人均有 Unit 8200 背景。公司总部在纽约，并在特拉维夫设有办公室。公司宣布完成 Seed 和 Series A，合计融资 5,300 万美元，投资方包括 TLV Partners、Maor Investments 和 Glilot Capital。估值未披露。

**解决的问题**

Agent 让企业内部更多员工和自动化系统都能创建数据工作负载，工作负载数量、代码形态和资源需求变得更分散。传统 Airflow/dbt/Databricks Workflows 主要负责编排，云 Autoscaler 主要按资源指标扩缩容，FinOps 工具主要给出成本分析；它们未必能跨引擎、代码、硬件和 SLA 联合优化每一次执行。

**核心技术与执行路径**

客户向 Zipher 提供工作负载代码、SLA 和预算。Zipher 的 Agent 学习工作负载及其依赖，然后决定：

- 使用哪个计算引擎、硬件类型和配置；
- 使用哪个 Framework、语言和语法；
- 何时、何地运行，以及如何根据实时容量和负载调度；
- 是否重写工作负载代码或配置；
- 在运行前和运行过程中自动应用优化，而不只是给出建议。

官方产品资料还列出 Spot Instance 优化、理解历史执行上下文的 Application-aware Autoscaler，以及对一方/第三方代码进行自动优化等能力。公司公告称支持 AWS、Azure、Google Cloud，并集成 dbt、Databricks Workflows、Apache Airflow、Azure Data Factory、Terraform 等。

**商业验证与成熟度**

- 公司称已在多家 Fortune 500 企业运行生产工作负载；Hertz 是公开点名的客户。
- Hertz 的企业数据分析负责人称，不同工作负载的计算成本下降约 25%–40%，并维持季节性峰值期间的性能。
- Zipher 自己宣称客户可获得 40%–60% 的 cost-efficiency gains、最高 80% 更好的 SLA adherence，通常两周内看到结果。这些数字是公司披露，不是第三方统一基准。
- Growth Plan 为 Pay-as-you-go，公开提供 30 天、最多 100 个选定 Workload 的试用；Enterprise 定价为定制报价，未公开单位价格。

**竞品与风险**

与传统 Autoscaler 的差异在于它声称能同时改动代码、Framework、计算引擎和调度策略；与 Airflow/dbt 等编排产品并非简单替代关系，更像跨工具的执行优化层。真正的难点是自动改写代码后如何保证语义等价、幂等性、数据正确性、回滚和成本边界。生产环境必须验证审批策略、变更 Diff、Canary、回滚、审计、预算上限和故障归因，否则“零人工干预”本身可能成为风险源。

**独立判断**

这是值得重点跟踪的新公司：它把 Agent 的价值从“生成 SQL/代码”推进到“对数据基础设施做持续决策和执行”。如果跨引擎优化和 SLA 兑现成立，商业模式可能从按工具席位收费转向按节省成本/完成工作负载收费。下一步要验证其优化是否能跨客户泛化，以及代码改写和资源调度是否有可审计、可回滚的安全边界。

### 3. Matters AI 获 1.15 亿卢比融资：Agent 数据安全从静态盘点转向运行时数据流治理

- **发布日期：** 2026-11-24（Economic Times 报道时间）
- **重要性：** A
- **领域/类型：** AI Agent Security、AI × Database、Data Governance、Vertical/Enterprise AI；融资/商业产品
- **公司背景：** Matters AI 的创始人为 Keshava Murthy（CEO）和 Harsh Sahu（CTO），公司在 Bengaluru 和 San Francisco Bay Area 有团队。Economic Times 报道其获得约 1.15 亿卢比、约 1,200 万美元融资，由 Tanglin Venture Partners 领投，IIFL Fintech Fund、Piper Serica、Foster Ventures、Tetration Ventures 及既有投资方 Kalaari Capital、Endiya Partners 参与。报道所称累计融资约 1.75 亿卢比。估值和 ARR 未披露。

**产品定位**

Matters 将自己定位为面向企业数据的 AI Data Detection & Response（DDR）平台，覆盖 Cloud、SaaS、Endpoints、Browsers、Databases 和 On-premises。它要回答的不只是“哪些数据敏感”，还包括“数据从哪里来、经过谁/哪个 Agent、流向哪里、当前使用是否符合业务意图”。

**技术架构**

- **Data Intelligence：** 通过语义分类、ML/LLM 和上下文模型发现结构化与非结构化敏感数据。
- **数据流与身份关联：** 公司称使用 fingerprinting 与 eBPF 跟踪数据在设备、文件、用户和 Agent 之间的移动，并以企业知识图谱关联身份、角色和意图。
- **Detection Agent：** 监测数据库查询、文件修改和 AI 应用交互。
- **Prevention Engine：** 根据敏感度和运行时上下文执行 DLP/访问控制，并与 Microsoft Purview 等系统协作。
- **Response Engine：** 编排账户隔离、Token 撤销、Endpoint Lockdown 等处置动作。
- **AI Data Guardrails：** 覆盖 RAG 数据源可见性、MCP 监控、Prompt/Output 检查和 Agentic Redaction。

**商业验证与成熟度**

Economic Times 报道公司称平台已部署在 50 多家组织，涉及金融机构、证券/资管、零售和数字媒体等领域；具体客户名单、ARR、合同金额、定价和独立效果评估未披露。产品网站展示了与 PayU、Groww、CRED、CreditSaison 等企业相关的客户引述，但这些属于厂商网站材料，不能直接等同于独立客户案例。

**竞品与风险**

竞品横跨 DSPM、DLP、Database Activity Monitoring、Insider Risk 和 Agent Security，包括 Microsoft Purview、BigID、Cyera、Varonis、Netskope 等类别。Matters 的差异化主张是把数据语义、设备级数据流、身份/意图和自动处置合并到一个控制平面。难点在于跨系统身份映射、eBPF 覆盖边界、误报率、实时阻断延迟，以及 Agent/MCP 工具的策略语义能否真正落到执行层。

**独立判断**

这类产品的价值不在于再做一个 Prompt Firewall，而在于把企业数据血缘、访问身份和运行时行为连起来，形成可审计的“谁/哪个 Agent 在何种上下文下对什么数据做了什么”。融资和 50+ 部署披露构成初步商业信号，但仍需客户案例、误报/漏报数据、策略覆盖和真实阻断效果来验证。当前更适合列入重点商业观察，不宜仅凭“AI Security Engineer”命名认定其已实现自主安全运营。

### 4. MemT-1.0 v5 与三档模型发布：把长期记忆做成模型内部状态，而非外置 RAG

- **论文版本日期：** 2026-11-23（arXiv v5；论文 v1 首次提交于 2026-10-19）
- **重要性：** A
- **领域/类型：** Agent Memory、AI × Storage、LLM Architecture、Agentic Coding；学术技术报告/模型发布
- **团队与状态：** arXiv 页面列出 Zhiyu Li 等 74 位作者；论文标注 MemTensor × NVIDIA 合作。当前是 arXiv 技术报告/预印本，不是已确认的同行评审会议论文。论文、模型卡和代码仓库均已公开。

**核心架构**

MemT-1.0 的目标是将持久、动态演化的记忆作为模型计算的一部分。它在 Backbone Attention 旁增加 Native Memory Block：

1. Local Memory Block 保存随交互演化的动态多通道状态；
2. Hyper Memory Block 提供可训练的 Query/Key/Value 投影，以及 Erase、Write、Forget、Output Gate；
3. 使用 Gated DeltaNet-2（GDN-2）进行稳定的 Token-level Memory Update；
4. 通过 Mixture-of-Storage（MoS）扩展记忆容量。

它不是简单地把历史文本塞进更长 Context，也不是外部 Vector DB 检索后拼接 Prompt，而是让模型在推理过程中直接读写一个持久状态。

**模型家族**

| 模型 | Backbone | 总参数 | 激活参数 | 可训练记忆参数 | 单轨迹动态记忆状态 |
|---|---|---:|---:|---:|---:|
| Nano | Qwen3.6-35B-A3B | 36B | 3B | 451M | 10M |
| Flash | DeepSeek-V4-Flash | 288B | 17B | 3.61B | 336M |
| Pro | NVIDIA Nemotron-3-Ultra-550B-A55B | 554B | 59B | 4.23B | 13M |

**实验与证据边界**

- 论文使用 34B tokens 训练数据，并在 11 个 Memory Benchmarks 上评测。
- 在作者评测的 Parametric Memory 方法中，Pro/Flash/Nano 排名第一/第二/第三；但论文也明确指出，强 Textual Memory 系统在整体上仍领先，尤其是需要长历史精确证据检索的任务。
- 在 128K 历史长度下，Nano 相比 Full-context KV Cache，作者报告约 1.86× 端到端推理加速、约 66× 持久状态存储缩减。这里比较的是持久 Memory State 与 Full-context KV Cache，不代表整个模型显存或系统成本都缩小 66 倍。
- 推理效率实验使用两张独占 GPU、Concurrency=1、Batch=1；论文没有在该实验段落披露具体 GPU 型号。不能把结果直接外推到高并发生产 Serving。
- Agentic Coding 使用 SWE-bench Verified 500 个任务和 SWE-bench Multilingual 300 个任务，每任务独立运行三次。Nano 在 Verified 的 Before Execution 设置下平均成功率为 69.33%，无经验基线为 66.07%，Textual Experience 为 68.87%；在 Multilingual 上分别为 62.89%、60.00%、64.22%。提升存在，但并非压倒性胜出。
- 作者指出当前仍依赖外部构造的 Experience Bank，效果取决于经验质量和检索；记忆写入也有计算开销，减少文本 Context 不等于总成本必然下降。

**开源与许可证**

- Nano 权重：Apache-2.0。
- Flash 权重：MIT。
- Pro 权重：OpenMDW-1.1。
- GitHub 推理/训练代码仓库：PolyForm Noncommercial License。不能把模型权重许可和代码许可混为一谈，也不能笼统称整个项目为 OSI 开源。
- 论文为 CC BY-NC-SA 4.0。

**独立判断**

MemT 的重要性在于把 Agent Memory 从外部检索系统推进到模型内部状态，可能改变长周期 Agent 的 Context/Storage 数据路径。但它并没有证明外部记忆数据库会消失：结构化事实、可追溯证据、跨模型共享、权限、审计、删除和冲突解决仍需要外部系统。建议重点复现 128K 长历史下的存储/延迟结果，并对比 MemOS、Mem0、Graphiti、OpenViking 等文本/结构化记忆系统；同时检查 Pro 的许可证边界和实际推理资源门槛。

### 5. NightWatch：用 0.8B Watcher 为 Computer-Use Agent 增加主动感知

- **论文首次公开：** 2026-11-21
- **重要性：** A
- **领域/类型：** Agent Runtime、Computer Use、Evaluation、AI Infrastructure；学术预印本/开源 Artifact
- **团队：** Jiaqi Su（National University of Singapore）、Jie-Jing Shao 与 Haiyan Yin（A*STAR Centre for Frontier AI Research）、Yichen Liu（SenseTime）、Long-Kai Huang（Hong Kong Baptist University）。
- **论文状态：** arXiv:2611.28947 v1，预印本，未标注顶会录用。

**研究问题与系统方法**

多数 Computer-Use Agent 采用“截图—推理—动作—固定 Sleep—再截图”的时间触发循环。VLM 推理期间，页面可能继续加载、弹窗、跳转或刷新；Agent 在真正执行动作时可能面对过时状态。NightWatch 不改变原 Agent 的模型、Prompt 或 Action Space，而是在 Agent 与环境之间加入一个轻量级 Watcher：

- Watcher 以 10 Hz 监视界面帧流；
- 使用 0.8B System-1 模型回答固定问题集合；
- 确定性控制器执行三类干预：Interrupt（界面变化使当前推理过时时中断）、Void（目标已变化时作废待执行动作）、Wake（界面稳定后立即唤醒 Agent，替代固定等待）。

论文报告 Watcher 使用一张 NVIDIA L40S GPU；其作用是判断何时重新观察和动作是否仍有效，不负责替代主 Agent 的任务推理。

**实验设计与结果**

- OSWorld-Verified：100 个任务，覆盖 10 个应用类别。
- DynaCU-Bench：49 个动态网页任务，包括 Live Dashboard、Carousel、Video、Game 等。
- 每个任务运行三次；比较时保持 Agent、Prompt、Action Space 和 Step Budget 一致。
- 大型 VLM（MiMo-V2.6-Flash）在 OSWorld 上：非推理时间由 197.4 秒降至 132.7 秒（减少 33%）；Wasted Time 从 16.3% 降至 7.7%（减少 53%）；成功率为 68.0% 对 66.3% 的 Vanilla。
- 同一大型 VLM 在 DynaCU-Bench 上：成功率由 39.5% 提升至 44.2%。
- 对 OSWorld 的非推理时间下降，论文报告配对检验 p=0.026；小模型设置 p=0.016。上述均为作者实验，不是第三方复现。

**实质差异与局限**

NightWatch 的贡献不是“再多看几张截图”，而是将观察时机变成事件触发，并允许中断过时推理、作废过时动作。与只缓存 Keyframe 的被动监视方法相比，它直接控制 Agent 的观察—行动时序。

局限也很清楚：它改变的是 Agent 何时感知，不是 Agent 如何推理；论文指出一部分失败仍来自 Agent 自身推理错误。对于界面变化速度超过 Agent 推理/动作延迟的极端场景，新的观察也可能在动作发出前再次过时。评测规模为 100+49 个任务、每任务三次，仍需要更大规模和第三方复现。

**Artifact 与成熟度**

- [GitHub 代码](https://github.com/SuJQ0722/NightWatch)：Apache-2.0；包含 Harness、Watcher 训练、配置、实验脚本和 Tests。当前仓库仍处于早期发布状态，提交历史很短。
- [Watcher 权重](https://huggingface.co/nullptr04/NightWatch-0.8B)
- [训练数据集](https://huggingface.co/datasets/nullptr04/NightWatch-Data)
- 代码提供 pytest、模拟端到端测试及 OSWorld/DynaCU 运行脚本；完整复现仍需要模型服务、GPU 和相应 Sandbox 环境。

**独立判断**

NightWatch 指向一个常被忽略的 Agent Runtime 瓶颈：长任务的效率不只取决于模型推理速度，还取决于 Agent 何时观察、等待多久、如何判断动作是否过时。值得把它与 Browser/OS Agent 的事件总线、DOM 变化监听、动作取消、Checkpoint 和 Replay 一起研究；下一步重点验证在多窗口、多任务、高并发和真实企业桌面中的收益与额外 GPU 成本。

## 二、今日产业与学术判断

### 1. Agent 开始成为数据平台的“工作负载生产者”，而不只是数据库的查询客户端

Zipher 把 Agent 放进数据工作负载的生成、代码优化、引擎选择、资源调度和执行闭环；ClickHouse 则把 MCP、AgentCore、Postgres 状态、Langfuse Trace/Eval、安全遥测组合成 Agent-ready Data Stack。两者路径不同，但共同指向：Agent 数量增长后，基础设施不再只服务人类工程师，而要理解并管理 Agent 产生的工作负载。

对数据库厂商的影响：需要提供 Agent 可理解的 Schema/Semantic Layer、权限、执行计划、成本预算和状态接口；对 Data Engineering 的影响：编排系统可能从 DAG Scheduler 演进为以 SLA、预算和数据正确性为约束的自治执行层。

### 2. Agent Memory 正在分化为“模型内存”与“外部可治理状态”两条路线

MemT 把历史压缩为模型内部持久状态，追求低存储开销和经验复用；AgenticOS 研究则把共享状态、并发、事务恢复、Context 生命周期和系统级调度当作 OS 层问题。两条路线不是替代关系：模型内记忆适合压缩和个体经验，外部数据库/对象存储适合跨模型共享、精确查询、权限、审计、删除和一致性。

未来的 Agent Memory Stack 很可能同时包含模型内状态、外部 Memory DB、对象/文件存储、事件日志和事务层。评价指标也不应只看 Recall Accuracy，还应包括 Cost、Latency、Update/Forget Correctness、Provenance 和可恢复性。

### 3. Agent 安全正在从 Prompt Guardrail 转向数据血缘、身份和运行时执行控制

Matters 的产品路线强调数据在 Cloud、SaaS、Endpoint、Database、MCP 和 Agent 间如何移动；AgenticOS 的议题则强调 Isolation、Access Control、Observability、Provenance 和 Governance。企业 Agent 安全的关键问题不是单次 Prompt 是否安全，而是某个 Agent 在某个身份、工具和业务上下文下，是否有权读取、复制、修改或外传特定数据。

这会推动 Database Activity Monitoring、DLP、DSPM、IAM、MCP Gateway 和 Agent Runtime Policy 逐步融合。真正的产品门槛是可验证的策略执行、误报率和审计闭环，而不是简单增加一个 LLM 检测器。

### 4. Agent 运行效率的瓶颈开始从模型 Token 转向端到端系统时序

NightWatch 证明在特定 CUA 基准上，固定 Sleep 和过时截图会带来明显浪费；Zipher 则把执行引擎、硬件和调度纳入优化。两者共同说明，Agent 的端到端性能应按 Task Completion Time、等待、工具/API、数据访问、资源竞争和失败恢复来度量，而不能只比较 Token/s 或单次模型延迟。

## 三、Agent 专项观察

**今日 Agent 专项有可靠新增，不能归结为“无更新”。**

- **产品/公司：** Zipher 是 Agent-driven Data Workload Management 的新进入者；Matters AI 把 Agent 数据访问安全纳入 DDR/DLP/DSPM 控制平面。
- **Runtime/Harness：** NightWatch 通过 Interrupt/Void/Wake 处理 Computer-Use Agent 的异步界面变化，代码和模型 Artifact 已公开。
- **Memory/Context：** MemT-1.0 展示模型内持久记忆；但外部数据库在共享、权限、删除和审计上的作用仍然存在。
- **安全/治理：** Matters 的 eBPF/fingerprinting、数据血缘和 MCP Guardrails 是值得跟踪的产品化路线；需要进一步验证策略的可执行性与误报。
- **共享状态与事务：** NeurIPS 2026 AgenticOS Workshop 的 Accepted Papers 中，Arizona State University 的 Kunal Jadhav、Siddhesh More 有一篇 Oral Paper：**Recoverability-Conditioned Concurrency Control: A Transactional Layer for Agents That Share State（AC-Saga）**。其方案在 PostgreSQL 前加入事务层：不可逆操作或已暴露的 Saga 强制加锁，可恢复操作再由小型 Q-learning 策略选择乐观/锁定执行；Abort 时根据语句和 Pre-image 重放确定性逆操作，若会覆盖其他 Agent 的写入则拒绝补偿。
  - 作者在真实 PostgreSQL、6 个 Agent、4-step Saga、30% 不可逆步骤、10 seeds 的单节点 YCSB-style 测试中报告 5,400 次尝试零 catastrophe；高竞争下 OCC catastrophe rate 为 10%。但其测试仅覆盖单行操作，且高竞争下 Tail Latency 上升 27%；补偿拒绝覆盖并发写入时 Saga 仍可能部分执行。
  - 该论文是 AgenticOS Workshop Paper，不是 NeurIPS 主会论文；Workshop 明确说明 non-archival、无正式 proceedings。当前 Workshop 页面没有代码链接，本次未找到可核实的公开 Artifact。
- **Evaluation/可观测性：** AgenticOS 还收录 DolphinBench（通过行动评估 Agent Memory）、VerifierContractBench、Windowed-MTP、Adaptive KV Retention 等议题，说明评估重点正在从问答准确率扩展到任务行为、状态管理、KV/Context 成本和可审计执行。
- **商业化：** Zipher、Matters 的融资与客户披露值得跟踪，但都需要继续区分厂商自述、试点、生产部署和可验证 ROI。

AgenticOS Workshop 将于 2026-12-11 在 NeurIPS Sydney 举办。官方页面列出 46 篇 Accepted Papers，其中 4 篇进入 Oral/Spotlight。Workshop 的系统研究范围覆盖 Agent OS 抽象、Memory/Storage、调度、资源管理、长周期执行、Governance、Evaluation；这比单独比较 LangGraph/CrewAI 等 Framework 更接近 Agent 全栈系统问题。
